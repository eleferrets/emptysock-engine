## Process decisions — 2026-09-22 (how this pass is actually run, not what it builds)

Settled with the project owner, alongside everything else in this file. Re-read before starting a new track or a new session on this pass.

- **No real game/deadline/platform constraint drives this.** Confirmed with the project owner: this is a clean engine-only rebuild, not migration for an existing shipped game. Touch/input/performance decisions are made on general mobile/tablet/desktop merit, not a specific device or store requirement.
- **Sequential execution, one session at a time — no parallel agents per track (for now).** Tracks 1–6 are _designed_ to be parallelizable once Track 0 lands, but the project owner chose sequential for now: do Track 0, then work through 1–6 one at a time in the same continuous thread. Revisit this if a future session finds the sequential pace is the actual bottleneck — the tracks were written to make that switch possible later without replanning.

- **No CI workflows exist in this repo** (`.github/workflows` is empty) — there's no automated gate enforcing any of the above. `pnpm run typecheck`/`test`/`lint` are the only checks, and they're run manually per commit/session, same as this session's baseline check. Don't assume a CI pipeline will catch a regression between sessions; each session re-running the full check before and after its own work is the actual safety net.

## Scope addition — 2026-09-22: mobile/tablet/desktop, touch + touchpad, everywhere

Decided with the project owner alongside the ECS-core pass below, applying to **both** the runtime engine and `apps/ide` — not just shipped games. This is not a separate pass; fold it into the tracks below wherever they touch input or rendering.

- **Both the IDE and the runtime get first-class multi-input support.** `apps/ide` (rc-dock panels, canvas/inspector interactions) must work with touch and touchpad gestures, not just mouse+keyboard. The engine's `InputManager` gets pointer/touch/touchpad parity alongside its existing keyboard/gamepad snapshot.
- **Pointer Events + `touch-action` for discrete pointer/touch/multi-touch.** `pointerdown/move/up` + `PointerEvent.pointerType` is the correct unification of mouse/touch/pen (W3C-stable, broadly supported) — do not hand-roll separate mouse/touch listeners. Use CSS `touch-action` to opt out of native gesture handling per-element, not `preventDefault()`.
- **Trackpad pinch/two-finger-pan is structurally different and needs its own path.** Trackpads report as an ordinary single mouse pointer — pinch/pan never reaches Pointer Events. Trackpad pinch surfaces as a `wheel` event with `ctrlKey: true` (`deltaY` as scale delta); two-finger pan is a plain `wheel` event with both deltas. Safari fires a proprietary `GestureEvent` instead and needs its own branch. Because `wheel` deltas are event-driven deltas (not sampleable state like a key or gamepad axis), the frozen per-frame input snapshot needs a dedicated **accumulator**: sum `wheel` deltas into the frozen snapshot each frame, then reset — don't try to force this through the same "read current state" model `isDown`/`gamepad()` use.
- **Render Layers, not hand-rolled zIndex bookkeeping, for the `LayerSystem` redesign (Track 2).** PixiJS shipped native **Render Layers** in v8.7 (`pixijs.com/blog/8.7.0`) — controls render order independent of scene-graph parentage, explicitly positioned as the successor to the unmaintained `@pixi/layers` plugin (dead since v2.1.0, never updated for v8). Build the per-`Scene`-scoped `Layer` component on top of this, not on manual `sortableChildren`/`zIndex` juggling. Docs mark the Render Layers API as still experimental — pin the exact pixi.js version tested against and re-verify on any pixi.js bump.
- **Coroutine cancellation (Track 0's `CoroutineSystem` port): version-keyed liveness check _plus_ `AbortController`.** The version-keyed-handle + pre-resume liveness check (already planned) is confirmed sound — it's the same shape as Bevy's own `Task<T>` cancel-on-drop. Add: wire an `AbortController` per coroutine, aborted on `Scene.destroy()`, so nested async work (fetches, sub-awaits inside the coroutine body) cancels structurally instead of relying solely on a manual check at every resume point.
- **Scene-transition crossfade (Track 6 / ground rule 11): budget the cost, no built-in shortcut exists.** PixiJS v8's `renderer.render({ target: renderTexture, container })` (object-form call) is the confirmed current API for rendering a scene to an offscreen texture; there is no built-in crossfade/transition utility in pixi.js core, so `RenderPipeline`'s planned overlay-`Graphics`-plus-two-`RenderTexture`-passes approach is the only path, not a stopgap for something better upstream. No documented perf number exists for the double-render-pass cost — profile explicitly on target devices (including lower-end tablets) before deciding whether true crossfade is the default or an opt-in mode per ground rule 11's original framing. Set `antialias` explicitly on both render textures (it is not inherited automatically in v8).
- **Library versions confirmed current as of 2026-09-22** (re-check again before Track 0 actually starts, this drifts): `pixi.js` 8.20.1 (pinned `^8.6.1` in `pnpm-workspace.yaml` — bump before starting Track 2 to pick up Render Layers, which landed in 8.7), `bitecs` 0.4.0 (already pinned, stable), `@dimforge/rapier2d-compat`/`rapier3d-compat` both at 0.20.0 (pinned `^0.14.0` — bump before Track 0/physics work). The deterministic Rapier builds (`-deterministic-compat`) lag the mainline compat builds (last seen ~0.19.3, ~8 months stale) — since these are dynamically `import()`-ed by a non-literal specifier (see CLAUDE.md) and are `optionalDependencies`, verify the exact deterministic version compatible with whatever mainline version gets pinned, don't assume they track in lockstep.

## Scope hardening — 2026-09-22: library-first, no hand-rolling

**Decided with the project owner: this pass is not just "one object model," it's "as little engine-original code as this can honestly get away with."** Every hand-rolled system gets a real library-or-hand-roll decision, not an automatic port — but "library-first" means preferring a real library **once auditing the actual code shows a real gap**, not defaulting to a swap just because a system's name sounds like something a library commonly exists for. The first pass at this section (below, superseded) made exactly that mistake: it picked libraries by system _name_ off the reference table without reading the actual implementations first, and three of its four calls were wrong once the code was actually read. Left as a durable lesson for whoever runs Track 0's real audit: **read the file before recommending its replacement.**

**Corrected after actually auditing the code (2026-09-22, same day):**

- **UI layout (Track 3, supersedes hand-written measure/arrange) → `yoga-layout@3.2.1`. Confirmed, real gap.** Audited `packages/engine/src/ui/Widget.ts` and everything under `ui/widgets/` — there is no measure/arrange/flex logic anywhere; widgets are manually positioned. Meta's flexbox engine (powers React Native), now a single consolidated WASM+JS npm package with first-party TS types. Headless-Node-safe (WASM, zero DOM), MIT. Scope it narrowly: Yoga does measure/arrange math only, given a tree of nodes with style props — it never owns the tree or renders anything. The bitECS relations/hierarchy tree (ground rule 4a) stays the source of truth for parent/child; the adapter mirrors that structure into Yoga nodes, calls `calculateLayout()`, and reads x/y/w/h back onto a `Transform`/`Layout` component. Yoga needs async `loadYoga()` init (WASM) — confirm this composes cleanly with the engine's synchronous boot path before committing.
- **Tweening (Track 4) — REVERSED, keep hand-rolled `TweenSystem`.** Audited `packages/engine/src/systems/TweenSystem.ts` (166 lines): already a plain synchronous `dt`-driven `TweenManager` with zero RAF/DOM dependency — exactly the shape a library would need to provide, already provided. It also does timer/repeat scheduling (`after()`/`every()`) that `SequenceSystem` depends on, which `@tweenjs/tween.js` doesn't cover — adopting it would mean keeping half the current file anyway just for the timer logic. Only 4 real references in the whole repo. No real problem exists here for a library to solve; the prior recommendation to adopt `@tweenjs/tween.js` is withdrawn.
- **Particles (Track 4) — REVERSED, keep hand-rolled `ParticleSystem`/`ParticleEmitter`.** Audited `packages/engine/src/systems/ParticleSystem.ts` (275 lines): it is **already a pure, renderer-agnostic simulation with zero pixi import** — its own comment says "the display layer handles actual rendering." Its only real consumer today is the IDE's `ParticleEditor.tsx` preview panel, which draws to a plain HTML canvas, not PixiJS — it was never actually wired into `RenderPipeline` for real gameplay rendering. Confirmed via research: PixiJS v8's own `ParticleContainer`/`Particle` (core, already available, no new dependency) is rendering-only by design — no spawn-rate/lifetime/velocity/emitter API exists anywhere in pixi core, and a third-party emitter package (the original `@pixi/particle-emitter`, unmaintained for v8 since a March-2024 open issue, or its single-maintainer v8 fork `@spd789562/particle-emitter`) does exactly what this engine's own file already does. Adopting the fork would replace working, dependency-free, renderer-agnostic code with a single-maintainer Pixi-specific package for no behavioral gain. **The real gap is wiring, not simulation**: add a `RenderPipeline` path that reads `ParticleEmitter.getParticles()` each frame and writes the result into a pixi `ParticleContainer` for actual in-game rendering — that's the only new work needed here.
- **Pathfinding (Track 5) — REVERSED, keep hand-rolled `AStarSearch`/`PathfindingSystem`.** Audited `packages/engine/src/core/AStarSearch.ts` (211 lines): it is **already** a generic, binary-heap A\* over a caller-supplied `neighbours()`/`key()`/`heuristic()` interface, with its own doc comment explaining it was factored out specifically so grid pathfinding (`PathfindingSystem`) and polygon-graph pathfinding (`@emptysock/tilemap`'s `NavMeshSystem`, confirmed calling `AStarSearch<NavPolygon>` directly) share one implementation instead of two hand-rolled copies. This is exactly the unification `ngraph.path` was recommended to provide — already done, already correct, already shared. A library swap here would be a lateral move at best; withdrawn.
- **Gesture/touch/trackpad (Track 1's new scope) — REVERSED, keep hand-rolled `PointerSystem`.** Audited `packages/engine/src/systems/PointerSystem.ts` (518 lines): it already hand-rolls tap/longpress/swipe/pinch gesture recognition, and **already** distinguishes trackpad pinch from mouse-wheel via the `ctrlKey` heuristic (a documented, working implementation of the exact "trackpad pinch surfaces as `wheel`+`ctrlKey`" pattern the prior session's research flagged as a gap) — with an explicit existing code comment stating the hand-roll-vs-library decision was made deliberately: "No third-party gesture library is used — the gesture surface area here... is small enough that a hand-rolled [detector is reasonable]." One real, small gap found: no explicit Safari `gesturestart`/`gesturechange` `GestureEvent` listener as defense-in-depth alongside the `ctrlKey`+`wheel` path — that's a same-file addition to `PointerSystem`, not a reason to take on `@use-gesture/vanilla` as a dependency. The prior recommendation to adopt `@use-gesture/vanilla` is withdrawn.

## The pass: make the ECS core the one engine, delete everything else

**Decided with the project owner on 2026-09-22, before any of this is implemented. Read this whole file before writing code or launching a sub-agent.**

The engine currently has two real, different object models living side by side: the ECS core at `packages/engine/src/ecs/` (bitECS-backed, `entity.get(Component)`/`scene.each()`, versioned entity IDs, currently covers only physics, sprite/transform rendering, save, and a query bridge) and the original `Scene`/`Entity`/`Component` at `packages/engine/src/core/` plus 32 systems under `packages/engine/src/systems/` (class-based, `entity.getComponent("Name")` keyed by a type string). This was a deliberate, incremental choice by the original design spec — not a mistake — but it is not where the engine ends up.

**The ECS core becomes the one real API. Every old system gets ported onto it or deleted. The old class-based `Scene`/`Entity`/`Component` goes away entirely.** Scope is everything: this repo's code, this repo's docs (`docs/`, `docs/manual/`, `docs/architecture.md`, every guide), `emptysock-ai-skills` (every skill file, `ai/CLAUDE.md`, `ai/AGENTS.md`, `ai/.cursorrules`, `ai/api-reference.json`), and `emptysock-mcp` (tool contracts and docs). Nothing old gets left behind anywhere, in code or in docs, in any of the three repos. This is a full redo, not a patch — expect a multi-session rewrite with a lot of real deletion at the end of it, not a quick pass.

**Documentation changes are last, across all three repos, full stop.** Don't touch `docs/`, `emptysock-ai-skills`, or `emptysock-mcp`'s docs until every code track below is done, parity-checked, and the old code is deleted. Writing docs against code that's still being ported means rewriting the docs again once the port's real final shape settles — wait until it's real.

## Ground rules (settled, don't re-litigate)

These were worked through explicitly with the project owner. If a session hits a moment that feels like it's re-deciding one of these, it's misreading the rule, not finding a real exception — stop and re-read this section.

1. **Versioned entity IDs stay as a real guarantee.** A stale `Entity` handle to something destroyed must fail loudly, not silently alias onto a newly-spawned entity. Native to the ECS core already — nothing extra to build for it, just don't lose it while porting something else.
2. **Audit real usage before porting or deleting anything.** Don't assume the directory listing below is gospel by the time you read it, and don't assume a system is load-bearing just because it exists. Check real callers first (Track 0 does this for the whole list up front; re-check narrowly for your own track before you start).
3. **Rollout is system by system, never a big-bang cutover.** Port one system, update its real consumers, verify it, move to the next. The old `Scene`/`Entity` stays alive and working for whatever hasn't been ported yet. `apps/ide` and the toolchain must never be broken mid-pass — every commit should leave a working engine.
4. **Not everything becomes a component.** Only genuinely per-entity data (something one specific entity _has_) becomes an ECS component. Process- or scene-global state (`PluginSystem`, `VariableStore`, `ActorSystem`'s message-passing) becomes a typed `Game` service instead (the same pattern already established for `game.audio`/`game.services`), not entities with components.
   4a. **Superseded 2026-09-22 for the widget tree specifically:** the UI widget tree (`UISystem`) does become one entity per widget, using bitECS's real relations/hierarchy module (`Relation`/`createRelation`/`Hierarchy`/`Cascade`/`queryHierarchy`, shipped in the already-pinned `bitecs@0.4.0` — verified as genuine first-party API, not experimental, exercised by real consumers like Hubs/Third Room). Build the parent/child edge via `createRelation` with `withAutoRemoveSubject` (destroying a parent widget cascades to children automatically) and drive measure/arrange layout passes with `queryHierarchy`/`Cascade` for guaranteed parent-before-child ordering. This replaces "the tree stays a tree" from the original ground rule 4 — the relation itself carries the tree structure instead of an external tree object, removing the "external tree out of sync with ECS state" bug class. **Prototype against one non-trivial subtree (a scrollable list) before wiring this through the whole widget system**, per the project owner's decision — confirm query performance holds at realistic widget counts (hundreds, not the tens-of-thousands bitECS is optimized for; it will very likely be fine, but verify before committing Track 3 to this shape).
5. **Parity required before deleting the old implementation of anything.** For each ported system, write tests exercising the same real scenarios the old system's own tests cover (43 old test files to draw from — use them as your scenario list, don't invent a thinner set) and confirm the new one behaves the same way. Don't delete on faith.
6. **Final layout: flatten `ecs/` back to the package root once the old code is gone.** `packages/engine/src/ecs/Entity.ts` → `packages/engine/src/core/Entity.ts` (or the package root, matching this repo's "core primitives go in `core/`" convention) once there's no second implementation left to segregate it from. `@emptysock/engine/ecs` retires as a subpath in favor of plain `@emptysock/engine`. This is the very last code step, only once everything is ported, parity-checked, and deleted — never partway through.
7. **Unify `IDEBridge` and `QueryChannel` into one bridge**, as part of this pass, not a follow-up. `IDEBridge` exists to talk to the old `Scene`/`Entity`; once that's gone, fold its push-style live-snapshot behavior into (or replace it with) `QueryChannel`.
8. **Delete `core/ObjectPool.ts`.** `Scene.spawn`/`.destroy`'s built-in `{ pool: true }` already covers what it was for.
