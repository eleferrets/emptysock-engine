## HOW TO: verify GMS2 import end-to-end against a new real project

**Written 2026-09-24, for whichever session picks this up next.** The project owner's stated goal for
this importer: convert real, messy, years-old GameMaker projects onto this engine, fully working, with
nothing silently faked. Two real projects have been tested this way so far (both since deleted per the
rule below) and both surfaced real bugs that no synthetic fixture had caught — this playbook exists so
the next test doesn't have to rediscover the method from scratch. This section is a standing reference,
not a dated task — keep it updated with whatever the next real-project test teaches, don't archive it.

**This is explicitly separate from Track 10** (the `docs/`/`docs/manual/` rewrite and the
`emptysock-ai-skills`/`emptysock-mcp` companion-repo sweep, tracked further down this file). Testing more
GMS2 projects does not require or imply starting that rewrite — don't conflate the two.

### The non-negotiable rule: nothing from the uploaded project ever touches the repo or git history

A real project a user uploads for this purpose is their own property, often unfinished/unreleased work.

1. Extract the uploaded archive (`.yyp` root, `.yyz`, or a `.zip` wrapping either) into your **scratchpad
   directory only** — never anywhere under the repo working tree.
2. Build the toolchain once if `packages/toolchain/dist/` is stale: `pnpm --filter @emptysock/toolchain run build`.
3. Run the real CLI against the scratch extraction, output also to scratch:
   `node packages/toolchain/dist/cli.js import --from gms2 --project <scratch>/<proj>/<Name>.yyp --out <scratch>/out --verbose`.
4. Do all inspection/verification (below) by reading files under `<scratch>/out` and the extraction —
   never copy anything from either into the repo.
5. **Before finishing your turn**, `rm -rf` both the extraction and the output directory, then confirm
   `git status` in the repo shows nothing related. If you find a real bug and want a regression test,
   build a small, clearly-synthetic fixture from scratch (following `gms2-import.test.ts`'s existing
   house style) — never a trimmed-down copy of the real project, and never use any name, asset name, or
   string that appeared in the real project anywhere in a comment, test name, or commit message.

### What to actually check — informed by the two real bugs found so far, not just "did it crash"

A clean CLI exit and a migration report full of green-sounding words is not sufficient evidence the
import is correct — both real bugs found so far (2026-09-24) produced a **successful exit and a report
that looked complete**, and were only caught by looking past the summary numbers:

1. **Cross-check every "converted" count against the real file count on disk**, don't trust the report's
   own arithmetic. `grep -c '"objects/[^"]*\.yy"' <Name>.yyp` (etc. per category) gives the `.yyp`'s
   real resource-list count; `find <scratch>/<proj>/objects -iname '*.yy' | wc -l` gives what's actually
   present on disk. A real, long-lived GameMaker project routinely has FAR more entries in its resource
   list than exist on disk (stale/orphaned references — assets deleted from disk without being removed
   from the project file) — this is normal and not itself a bug, but every one of those must show up as
   a named, honest failure in the report, never a silent "converted." This exact gap (objects specifically
   were being silently faked as "converted" with a fabricated empty prefab when their `.yy` didn't exist)
   was the second real bug found — check whether it's still fixed, and apply the same "does this resource
   category check for real existence before claiming success" scrutiny to any resource kind you haven't
   personally re-verified recently.
2. **Read the actual generated file contents for a handful of real, successfully-converted assets** —
   don't just confirm the file exists and the report says "converted." Does a `.prefab.json` for an
   object with a real sprite actually have a `Sprite` component with the real texture path, or just
   `Transform`? Does an object with `physicsObject: true` actually get a `PhysicsBody`? This exact
   category of bug (`buildObjectPrefabJSON` silently emitting only `Transform` for every object,
   regardless of its real data, because it never read the source `.yy` at all) was the first real bug
   found, and it passed every existing synthetic-fixture test because none of those fixtures happened to
   assert on the specific fields that were missing.
3. **Actually run the generated behavior through the engine, don't just read the generated TypeScript
   text.** Build a small real runtime harness: construct a headless `Scene`, `registerGmlBehavior()` a
   generated `.behavior.ts` module, spawn its prefab via `loadSceneFile()`'s `onSpawned` hook (dispatches
   `onCreate`), step several frames via `GmlBehaviorSystem.update()`, and assert on real resulting state
   — did a `Transform` position genuinely change the way an `action_move` call in the source should cause?
   Does cross-entity Begin/Step/End-Step ordering hold? This is what caught `gmlActionsStep()` never
   actually being called by codegen despite its own doc comment claiming it was — a bug invisible from
   reading generated text alone, since the generated code was syntactically fine and merely didn't do
   anything.
4. **Every resource category the project actually contains, converted or not.** A big real project may
   exercise resource types no test has hit yet (tilesets, shaders, sequences, timelines, extensions) —
   confirm each either has a real conversion path or produces a clean, named "no import path in this
   tool" warning (never a crash, never a silent `skipped`-array-only entry with no report line).
5. **Read the migration report's own summary table** and sanity-check its arithmetic against the
   category-by-category counts above — a report that's internally inconsistent (converted + manual ≠
   found) is itself a signal something upstream miscounted.

### If you find a real bug

Fix it for real (not a report-only finding), add a synthetic regression test proving it (in whichever of
`gms2-import.test.ts` / `gms2-codegen-events.test.ts` / `GmlBehaviorSystem.test.ts` / a new file fits),
verify `npx turbo run typecheck lint test --force` green, update the relevant CLAUDE.md entry to describe
the real fixed behavior (not the old broken one), and add a dated bullet to this file describing exactly
what was wrong — the two entries already here (search "gms2 object prefab and stale-reference bugs") are
the model to follow: precise, with before/after examples, not vague.

## Track: adopt react-konva narrowly, scheduled before the Track 10 docs/skills/mcp rewrite

**Written 2026-09-24**, from a real audit (not a guess) of every canvas-drawing panel in `apps/ide`.

**Correction, same day, after the first audit pass:** the first pass claimed "no canvas panel uses
`react-konva`" — wrong. `ImageEditor.tsx` genuinely uses it: `Stage`/`Layer`/`Image`/`Line` drive its
actual interactive editing surface (brush strokes, eraser via `globalCompositeOperation`, pan/zoom), and
a separate plain offscreen `<canvas>` handles the operations Konva's vector-node model can't — flood-fill
(`getImageData`/`putImageData`, real per-pixel work) and undo/export snapshots (`toDataURL`). `stage.toDataURL()`
bridges the two: rasterize the Konva layer, do pixel ops on the bitmap, load the result back as an image
for Konva to display again. That's a deliberate, correct split, not a mishmash — the first audit's grep
for `getContext`/`<canvas` found `ImageEditor.tsx`'s offscreen-canvas half and missed that its visible
surface is Konva. Re-verified directly (not re-grepped) 2026-09-24: `grep -rl "from \"react-konva\""
apps/ide/src` returns exactly one file, `ImageEditor.tsx`; every other canvas-touching panel
(`CanvasPreview`/`NavMeshEditor`/`ShaderEditor`/`Profiler`/`VNPreviewPanel`/`TilemapEditor`/`VNMinimap`/
`UIPlacementPanel`/`ParticleEditor`) is still confirmed plain-canvas-only, zero Konva — that part of the
first audit held up.

**Net effect on this track: `react-konva` was never an unused/droppable dependency** — it's real,
load-bearing, single-consumer. The "drop it if unused" branch below is moot and should not be acted on.
What _does_ still hold from the first audit: per-panel conversion assessment for the panels that don't
yet use it is unaffected by this correction (Konva-fit-or-not is about each panel's own drawing needs,
not about whether some other panel already uses the library) — converting `NavMeshEditor.tsx`/
`UIPlacementPanel.tsx` is now extending an already-proven-in-this-codebase pattern, a smaller ask than
adopting a genuinely new dependency would have been, which if anything strengthens the case for doing it.

Goal, corrected: extend the already-real Konva pattern to the panels that would benefit
(`NavMeshEditor.tsx`, `UIPlacementPanel.tsx`, partially `TilemapEditor.tsx`), leave it alone where it
doesn't fit, land it before starting the Track 10 docs/skills/mcp rewrite so that pass documents the
IDE's actual, settled panel architecture rather than a mid-migration one.

**This is not an all-or-nothing conversion.** The audit found `apps/ide`'s canvas panels split cleanly
into two real categories — panels that author IDE-native shapes (a real Konva fit) and panels that
render _live engine/pixi simulation output_ or do _pixel-level raster editing_ (Konva does not apply,
full stop, regardless of migration effort). Converting the second category would replace working,
correctly-scoped code with a worse fit for no benefit — that is its own kind of technical debt, not
progress toward "modern." The audit also found the real shared-chrome payoff case (grid/ruler/snap/zoom
logic factored out of every grid panel) **already exists** — `apps/ide/src/lib/editorGrid.ts` +
`components/panels/shared/ViewControls.tsx` — and is not itself duplicated per-panel today. Adopting
Konva would change the rendering primitive underneath that existing shared layer, not newly deduplicate
anything.

## Scope addition — 2026-09-22: mobile/tablet/desktop, touch + touchpad, everywhere

Decided with the project owner alongside the ECS-core pass below, applying to **both** the runtime engine and `apps/ide` — not just shipped games. This is not a separate pass; fold it into the tracks below wherever they touch input or rendering.

- **Both the IDE and the runtime get first-class multi-input support.** `apps/ide` (rc-dock panels, canvas/inspector interactions) must work with touch and touchpad gestures, not just mouse+keyboard. The engine's `InputManager` gets pointer/touch/touchpad parity alongside its existing keyboard/gamepad snapshot.
- **Pointer Events + `touch-action` for discrete pointer/touch/multi-touch.** `pointerdown/move/up` + `PointerEvent.pointerType` is the correct unification of mouse/touch/pen (W3C-stable, broadly supported) — do not hand-roll separate mouse/touch listeners. Use CSS `touch-action` to opt out of native gesture handling per-element, not `preventDefault()`.
- **Trackpad pinch/two-finger-pan is structurally different and needs its own path.** Trackpads report as an ordinary single mouse pointer — pinch/pan never reaches Pointer Events. Trackpad pinch surfaces as a `wheel` event with `ctrlKey: true` (`deltaY` as scale delta); two-finger pan is a plain `wheel` event with both deltas. Safari fires a proprietary `GestureEvent` instead and needs its own branch. Because `wheel` deltas are event-driven deltas (not sampleable state like a key or gamepad axis), the frozen per-frame input snapshot needs a dedicated **accumulator**: sum `wheel` deltas into the frozen snapshot each frame, then reset — don't try to force this through the same "read current state" model `isDown`/`gamepad()` use.
- **Render Layers, not hand-rolled zIndex bookkeeping, for the `LayerSystem` redesign (Track 2).** PixiJS shipped native **Render Layers** in v8.7 (`pixijs.com/blog/8.7.0`) — controls render order independent of scene-graph parentage, explicitly positioned as the successor to the unmaintained `@pixi/layers` plugin (dead since v2.1.0, never updated for v8). Build the per-`Scene`-scoped `Layer` component on top of this, not on manual `sortableChildren`/`zIndex` juggling. Docs mark the Render Layers API as still experimental — pin the exact pixi.js version tested against and re-verify on any pixi.js bump.
- **Coroutine cancellation (Track 0's `CoroutineSystem` port): version-keyed liveness check _plus_ `AbortController`.** The version-keyed-handle + pre-resume liveness check (already planned) is confirmed sound — it's the same shape as Bevy's own `Task<T>` cancel-on-drop. Add: wire an `AbortController` per coroutine, aborted on `Scene.destroy()`, so nested async work (fetches, sub-awaits inside the coroutine body) cancels structurally instead of relying solely on a manual check at every resume point.
- **Scene-transition crossfade (Track 6 / ground rule 11): budget the cost, no built-in shortcut exists.** PixiJS v8's `renderer.render({ target: renderTexture, container })` (object-form call) is the confirmed current API for rendering a scene to an offscreen texture; there is no built-in crossfade/transition utility in pixi.js core, so `RenderPipeline`'s planned overlay-`Graphics`-plus-two-`RenderTexture`-passes approach is the only path, not a stopgap for something better upstream. No documented perf number exists for the double-render-pass cost — profile explicitly on target devices (including lower-end tablets) before deciding whether true crossfade is the default or an opt-in mode per ground rule 11's original framing. Set `antialias` explicitly on both render textures (it is not inherited automatically in v8).
- **Library versions confirmed current as of 2026-09-22** (re-check again before Track 0 actually starts, this drifts): `pixi.js` 8.20.1 (pinned `^8.6.1` in `pnpm-workspace.yaml` — bump before starting Track 2 to pick up Render Layers, which landed in 8.7), `bitecs` 0.4.0 (already pinned, stable), `@dimforge/rapier2d-compat`/`rapier3d-compat` both at 0.20.0 (pinned `^0.14.0` — bump before Track 0/physics work). The deterministic Rapier builds (`-deterministic-compat`) lag the mainline compat builds (last seen ~0.19.3, ~8 months stale) — since these are dynamically `import()`-ed by a non-literal specifier (see CLAUDE.md) and are `optionalDependencies`, verify the exact deterministic version compatible with whatever mainline version gets pinned, don't assume they track in lockstep.

## Ground rules (settled, don't re-litigate)

These were worked through explicitly with the project owner. If a session hits a moment that feels like it's re-deciding one of these, it's misreading the rule, not finding a real exception — stop and re-read this section.

1. **Versioned entity IDs stay as a real guarantee.** A stale `Entity` handle to something destroyed must fail loudly, not silently alias onto a newly-spawned entity. Native to the ECS core already — nothing extra to build for it, just don't lose it while porting something else.
2. **Audit real usage before porting or deleting anything.** Don't assume the directory listing below is gospel by the time you read it, and don't assume a system is load-bearing just because it exists. Check real callers first (Track 0 does this for the whole list up front; re-check narrowly for your own track before you start).
3. **Rollout is system by system, never a big-bang cutover.** Port one system, update its real consumers, verify it, move to the next. The old `Scene`/`Entity` stays alive and working for whatever hasn't been ported yet. `apps/ide` and the toolchain must never be broken mid-pass — every commit should leave a working engine.
4. **Not everything becomes a component.** Only genuinely per-entity data (something one specific entity _has_) becomes an ECS component. - `packages/engine/src/systems/RenderSystem.ts` (454 lines, read relevant sections). Confirmed the structural fact CLAUDE.md's "Why Draw GUI's camera-independence is a render-tree structural property" entry documents: `_root` (the one thing ever passed to `renderer.render()`) has exactly two children, `_stage` (what `CameraSystem.attach()` transforms) and `_guiStage` (camera-independent overlay). `renderFrame()`'s core call is `this._renderer.render(this._root)` — one renderer, one canvas, one render pass per frame, full stop. There is currently no `RenderTexture` use anywhere in `RenderSystem`/`RenderPipeline` for the main frame (the one prior use of `renderer.render({ target: renderTexture, container })`-style object-form rendering is discussed, not implemented, in CLAUDE.md's `SceneTransitionManager` entry, for a two-scene crossfade that was explicitly _not_ built for cost/profiling reasons).

No `pixi-viewport`, no `@pixi/particle-emitter`/`pixi-particles`, no 3D library anywhere in the monorepo today.

### Camera: real recommendation — hand-rolled multi-camera via N `RenderTexture` passes, `pixi-viewport` NOT adopted

**What `pixi-viewport` actually is, confirmed by reading its own README/issue tracker (`pixijs-userland/pixi-viewport` on GitHub) rather than assuming from the name:** it is a single `Container` subclass that adds pan/zoom/drag/wheel/pinch/follow/bounce/clamp _interaction_ plugins on top of one pixi container representing one camera's view into the world — i.e. it solves "let the player drag/zoom/scroll this one view," not "render N independent views of the same scene to N screen rectangles." Its own GitHub issue tracker has two _open feature requests_ asking for exactly this ("Feature request: multiple viewports of the same scene/game objects", #182; a minimap demo request, #305) with no resolution — confirming, from the library's own maintainers' backlog rather than an assumption, that multi-viewport composition is **not** something `pixi-viewport` provides today. Adopting it would add a real dependency that solves none of the actual multi-camera-rendering problem; at best it could replace `CameraSystem`'s own hand-rolled pan/zoom/lerp/bounds/shake math for a _single_ camera, but `CameraSystem.ts` (227 lines, read above) already implements that same feature set (lerp-based follow, zoom, rotation, screen shake, world/screen conversion, bounds clamping) in code this project already owns end-to-end, matches GameMaker's own `camera_set_view_pos`/`camera_set_view_speed`/etc. semantics `gmlCamera.ts` is transpiling onto, and needs no new dependency. **Recommendation: do not adopt `pixi-viewport`.**

**The real multi-camera design**, given what `RenderSystem`/`RenderPipeline` actually are (one `_root` → `renderer.render(_root)` per frame): each active camera slot needs its own render pass to its own `RenderTexture`, then all N `RenderTexture`s get composited onto the real screen canvas as textured quads/sprites positioned at each camera's screen viewport rectangle (`view_xport`/`view_yport`/`view_wport`/`view_hport` — already-real fields on `gmlCamera.ts`'s `GmlCameraHandle`, just not consumed by any renderer today). Concretely, this means:

1. `CameraSystem` needs to go from "one camera, transforms the one `stage` it's attached to" to something that can produce a camera _transform_ (position/zoom/rotation) without requiring exclusive ownership of the single main `stage` — likely: keep `CameraSystem` exactly as-is for the common single-camera case (per CLAUDE.md's existing "a camera is naturally per-scene ... game code constructs `new CameraSystem()`" decision, unchanged), and add a _new_, additive `MultiCameraRenderer`-shaped concept — not a `CameraSystem` rewrite — that owns N `CameraSystem` instances, each attached to its own scratch `Container`, and N `RenderTexture`s sized to that camera's `view_wport`/`view_hport`.
2. `RenderSystem.renderFrame()` (or a sibling method) would need to, per active camera slot: render `_root`'s scene content (or a camera-specific subset — GameMaker's `view_visible[]` masking is already tracked in `GmlCameraRegistry`) into that camera's `RenderTexture` via pixi v8's real object-form `renderer.render({ target: renderTexture, container })` API (the same API CLAUDE.md's `SceneTransitionManager` entry already names as real and available, just previously judged not worth the perf-profiling risk for a crossfade — multi-camera is a materially different, actually-requested feature, not the same tradeoff), then composite each `RenderTexture` as a `Sprite` positioned/sized at that camera's screen viewport rect in one final pass to the real canvas.
3. This is a genuine N-full-render-pass-per-frame cost (same caveat CLAUDE.md's transition entry already raises for a 2-pass crossfade, now for up to 8 passes) — needs real device profiling before landing, same "cannot be judged by a headless CI sandbox" caution that entry already states. For a game that only ever activates 1-2 camera slots at once in practice (most likely, even if 8 are technically declarable), the cost is bounded by _actual_ concurrent camera count, not the fixed 8-slot ceiling — worth instrumenting so the perf story is about real usage, not the theoretical max.
4. `gmlCamera.ts`'s existing `GmlCameraHandle`/`viewCamera[]`/`view_xport` etc. state already has everything a compositor needs (screen rect, angle, active/visible flags) — this is genuinely a rendering-side gap, not a data-model gap. The compat layer's data model does not need to change; only `RenderSystem`/`RenderPipeline` need the new N-pass-and-composite machinery, wired to read that existing state.

**Recommendation: keep `CameraSystem` as the single-camera building block, do not adopt `pixi-viewport`, and design a new additive multi-camera compositor in `RenderPipeline`/`RenderSystem` built on N `RenderTexture` passes + a final composite pass, using pixi.js core (already installed, no new dependency) — this is real, novel engine code that needs its own design/implementation pass and real-device perf profiling, not a drop-in library.**

### Particles: real recommendation — keep the hand-rolled `ParticleEmitter`, do not adopt `@pixi/particle-emitter`

**What `@pixi/particle-emitter` actually is, confirmed via its own npm/GitHub page (`pixijs-userland/particle-emitter`, formerly `pixi-particles`, current docs at `particle-emitter.pixijs.io`) rather than assumed from the name:** a config-driven particle system built around named "behaviors" (`AlphaBehavior`, `ColorBehavior`, `ScaleBehavior`, `RotationBehavior`, `MoveSpeedBehavior`, etc.), each independently configurable with multi-key curves via its own `PropertyList`/`ValueList` shape — genuinely more expressive on curve interpolation than this engine's current `sampleGradient()` (a plain N-point linear lerp across `colorGradient: number[]`, confirmed by reading `ParticleSystem.ts`'s own `sampleGradient`/`lerpColour` above) and than `gmlParticles.ts`'s documented 2-point alpha approximation. On paper this looks like a stronger match for GameMaker's actual `part_type_alpha3`/`part_type_colour3`/`part_type_speed`-style multi-key curve semantics than the hand-rolled emitter.

However, three things weigh against adopting it for _this_ project specifically, read from the actual gap list rather than assumed:

1. **The real gaps `gmlParticles.ts` documents are not curve-interpolation gaps.** Re-reading its own doc comments: blend mode is "stored, never applied" (an emitter-library-agnostic gap — GameMaker's additive/subtract blend modes need PixiJS `BlendMode` wiring on whatever renders the particles, `@pixi/particle-emitter` included, since blend mode is a renderer-container property, not a config-curve concern), shape bitmaps (`pt_shape_*`) are "stored, never rendered" (needs real sprite-sheet/texture-atlas work regardless of which emitter simulates the particles), and per-step wiggle is unimplemented physics, not a curve-shape limitation. Swapping the simulation library does not close any of these three — they are all rendering/data gaps that sit _above_ or _beside_ the emitter, and would need the same amount of new work either way.
2. **`@pixi/particle-emitter`'s config shape is a real config format to convert into from `gmlParticles.ts`'s GMS2-shaped `part_type_*` state** — this is nontrivial mapping work (behavior list construction, `PropertyList` curve conversion) that would have to happen either way, and the current hand-rolled `ParticleEmitter`/`_configToEmitterOptions` conversion path (already built, already tested, already wired to `RenderPipeline.mountParticles()`'s real `ParticleContainer` rendering) would need to be thrown away and rebuilt against a new library's shape for a benefit (richer curves) that is not the thing actually blocking the documented gaps.
3. `RenderPipeline.mountParticles()` already renders through a real, cheap, pixi-core `ParticleContainer` (CLAUDE.md's own entry) with no dependency beyond pixi.js core itself already installed — `@pixi/particle-emitter` would be a genuinely new dependency for a benefit narrower than it first appears.

**Recommendation: keep the current hand-rolled `ParticleEmitter`. Do not adopt `@pixi/particle-emitter`.** If GameMaker's real multi-key colour/alpha/speed curves turn out to matter for this specific project once a real project's particle systems are inspected, the more targeted fix is extending `ParticleEmitterOptions`/`sampleGradient` to accept real multi-key curves for `startAlpha`/`endAlpha`/velocity (closing `gmlParticles.ts`'s documented 2-point-approximation gap directly) rather than a wholesale library swap that leaves the blend-mode and shape-bitmap gaps exactly where they are today.

### Pseudo-3D projection: real recommendation — pixi.js v8 core's `PerspectiveMesh`, confirmed installed and exported, not a hand-rolled shader

This is the one place research changed the expected answer. Before assuming "pixi is 2D-only, this needs hand-rolled shader work," the actually-installed `pixi.js@8.21.0` package was inspected directly on disk (`node_modules/.pnpm/pixi.js@8.21.0/node_modules/pixi.js`), not just searched for online:

- `lib/scene/index.d.ts` re-exports `./mesh-perspective/PerspectiveMesh` and `./mesh-perspective/PerspectivePlaneGeometry` — both are real, shipped, core pixi.js v8 exports (not a plugin, not a separate package), confirmed present in the installed `node_modules` tree and therefore already available to `packages/engine` with zero new dependency.
- `PerspectiveMesh.d.ts` (read in full) and the package's own bundled `mesh-perspective.md` skill doc (also read in full) confirm exactly what it does: a `Mesh` subclass that warps a textured quad by four independently-movable corner points (`x0,y0`..`x3,y3`, clockwise from top-left), computing perspective-_correct_ UV interpolation across a configurable `verticesX`×`verticesY` grid (default 10×10). Its own doc is explicit about the honest limit: "This is not a full 3D mesh, it is a 2D mesh with a perspective projection applied to it" — no Z-buffer, no real camera, no true 3D — which is in fact exactly the pseudo-3D-in-a-2D-game shape GameMaker's own `d3d_transform_*`/legacy pseudo-3D tricks and the modern `camera_set_proj_mat` perspective-matrix functions are also faking (GameMaker itself has never had a real 3D pipeline for this class of trick either — it's projecting/skewing 2D sprites to fake depth, the same category of trick). The library doc's own worked "Fake floor" example (far corners higher/closer together on screen than near corners) is literally the road/floor-recedes-into-the-distance trick this kind of GameMaker project uses.
- This directly satisfies the pseudo-3D requirement for the common cases: billboarded sprites tilted/skewed to fake depth, a floor/road plane receding into the distance, per-frame animated corner warps (`setCorners()`, cheap — updates geometry in place, no reallocation) for a rotating/banking pseudo-3D effect. It does **not** provide real depth sorting, real occlusion, or a real projection matrix/camera — GameMaker's modern `camera_set_proj_mat` family, if the real project turns out to use _that_ API specifically rather than the legacy per-sprite `d3d_transform_set_*`/billboard style, implies actual scene-wide perspective-matrix semantics that a single warped quad per sprite does not automatically give you; determining which of the two APIs the real project actually calls (confirmed not yet determined — the task's own framing correctly flags this as still open) is the next concrete research step before design work starts, since it changes whether "one `PerspectiveMesh` per sprite, corners computed from a shared virtual camera/horizon line" is sufficient or whether a small custom projection-matrix layer needs to sit in front of it.

**What a new engine-side system would look like, concretely, once the legacy-vs-modern API question above is answered:** a new `compat/gmlProjection.ts` (sibling to `gmlCamera.ts`, same "GameMaker function name → engine call" pattern) holding the small amount of real GML-specific translation (angle/FOV/horizon-line math converting `d3d_set_projection`'s eye/target/up vectors, or `camera_set_proj_mat`'s 4x4 matrix, into per-sprite `PerspectiveMesh` corner coordinates), plus a `RenderPipeline`-side integration point that swaps a flagged `Sprite` entity's normal quad rendering for a `PerspectiveMesh` instance whose corners are recomputed from that translated state every frame. This is genuinely new, carefully-designed engine code — the _library primitive_ underneath it is real and already installed, but the GML-projection-math-to-corner-coordinates translation layer is not something any library provides, matching the task's own expectation that this would be "the hardest of the three."

**Recommendation: build pseudo-3D projection on pixi.js core's real, already-installed `PerspectiveMesh`/`PerspectivePlaneGeometry` (zero new dependency). Do not assume a hand-rolled shader/`Mesh` is needed from scratch — the corner-warp primitive already exists and is well-documented; the real remaining engine work is (a) determining which of GameMaker's two projection APIs the actual project uses, and (b) writing the GML-projection-parameter-to-corner-coordinate translation layer, not writing a WebGL shader.**

## 2026-09-25: "Rain on glass" post-process effect (implemented)

- [x] `RainGlassFilter` (`packages/engine/src/systems/RainGlassFilter.ts`) — a GPU-cheap, screen-space "rain on glass" filter (droplets/streaks on the camera lens, refracting the scene behind them, inspired by Asphalt 8: Airborne's on-screen rain effect), built to replace the user's prior GameMaker/GMS2 shader-based rain that "killed the game's performance in gms2".
  - **Technique:** a single pixi.js v8 `Filter` fragment-shader pass, following the exact `CustomShaderFilter.ts` mechanism (`GlProgram` + a `resources["uniforms"]` block, `uTime` updated once per frame) rather than inventing a second filter-building mechanism. Two overlapping procedural cell grids (large, near-static droplets and small, fast-falling streaks, blended by `streakAmount`) are generated per-pixel via a cheap hash function — no droplet list, no particle system, no displacement-map texture upload. Each cell's offset-from-centre gives a fake radial "normal" used to offset the `texture()` lookup into the already-rendered scene, the same idea a `DisplacementFilter` implements via a sampled texture, computed procedurally here instead.
  - **Perf characteristics vs. the naive per-pixel GMS2 shader approach:** cost is `O(screen pixels)` — two texture samples plus a handful of `hash`/`smoothstep` ALU ops per pixel, with no loops and no scaling with "how many raindrops are on screen." A typical naive GMS2 rain shader that got called out as killing performance is usually one of: (a) a real per-drop loop inside the fragment shader (cost scales with drop count, and GameMaker shaders commonly ran this per-pixel with no early-out), (b) a full-screen multi-pass blur/distortion combo re-run every frame with no caching, or (c) CPU-side per-drop sprite/vertex-buffer updates feeding the shader every frame. `RainGlassFilter` has none of these: it allocates nothing per frame (uniforms are patched in place via `setOptions()`/`tick()`, the same "rebuild only on type change" caching `syncPostProcessLayerFilters()` already uses for every other layer filter type), and its cost is bounded purely by resolution, not drop density or any CPU-side bookkeeping.
  - **Honest limits, stated in the file's own header comment:** this is a 2D screen-space approximation, not physically-based refraction — no lens geometry, no light bending through an actual water volume, no drops merging/sliding into each other over time. It reads as convincing "it's raining and the screen is wet," not a physical simulation.
  - Wired into `PostProcessSystem` as a new `"rain-glass"` `LayerFilterType` (options: `intensity`, `dropletSize`, `dropletSpeed`, `streakAmount`) and into `RenderSystem` following the exact `_createPostProcessFilter`/`_configurePostProcessFilter`/`syncPostProcessLayerFilters` split CLAUDE.md's "PostProcessSystem's layer filters become real pixi Filters" entry documents — one `RainGlassFilter` instance cached per layer id, `uTime` advanced by real wall-clock delta (`_tickRainGlassFilters()`), resolution kept in sync with the renderer's actual size.
  - `cssFilterForLayer()` honestly returns `''` for `"rain-glass"` — there is no CSS filter primitive that can express procedural per-pixel UV refraction (a host drawing a layer as a DOM element gets no visual effect for this type; a real pixi-backed `RenderSystem` is required).
  - Distinct from, and does not touch, the existing particle-based background rain (`ParticleEmitter`/`gmlParticles.ts`) — that remains the mechanism for rain falling through the world; `rain-glass` is purely a camera/lens-space overlay, and the two compose (particle rain in the world + rain-glass on the camera layer).
  - Exported from `packages/engine/src/index.ts`: `RainGlassFilter`, `createRainGlassFilter`, `RainGlassFilterOptions`.
  - Documented in `docs/manual/05-systems-reference.md` §5.13 (PostProcessSystem).
  - Tests: `RainGlassFilter.test.ts` (uniform defaults/overrides, `setOptions`/`setResolution`/`tick`, GLSL contract), `PostProcessSystem.test.ts` (options storage, `cssFilterForLayer` honest empty-string, composing with another layer's filter type), `RenderSystem.test.ts` (real `RainGlassFilter` attached/configured/reused/rebuilt through `syncPostProcessLayerFilters()`, `uTime` advancing across syncs). Full engine suite (`vitest run` in `packages/engine`): 60 files / 555 tests passing, no regressions. `npm run build:types` clean.
