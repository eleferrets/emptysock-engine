## 1. Headline findings

1. **The engine has no runtime path that renders UI widgets in a pixi game.** `UISystem.render(scene, ctx: IUIRenderer)` (ui/UISystem.ts:310) draws through a Canvas2D-shaped interface. Its only real caller is the IDE's UI Placement panel (apps/ide/src/components/panels/UIPlacementPanel.tsx:92,159,163), which owns a 2D canvas. `@emptysock/vn`'s `VNTextbox` (packages/vn/src/VNTextbox.ts:56-83) documents the same "caller calls `uiSystem.render(scene, ctx)`" contract. A shipped game's canvas belongs to a WebGL/WebGPU pixi renderer, which cannot also hand out a 2D context. grep over templates/, packages/toolchain, packages/battle finds no UISystem/WidgetTree/IUIRenderer use. So the widget stack is a tested foundation with no GPU-side consumer. The seam that "must be kept for headless tests" is the reason UI cannot ship. That reframes the question from "swap libraries" to "give widgets a pixi view".
2. **@pixi/layout works headless.** Verified: `new LayoutSystem(); await init(); update(root)` on plain `Container`s in Node with pixi 8.21.0 and yoga-layout 3.x computes correct boxes (row, gap, padding, flexGrow gave left/top/width/height as expected) and exposes them at `container._layout.computedLayout` with no renderer or DOM. The premise "adopting @pixi/layout loses headless layout tests" is false. The premise "it saves much code" is also false (section 3).
3. **`new Container`, `Graphics.roundRect().fill().stroke()`, `Text`, `Sprite` all construct and expose instructions/bounds in Node** (verified). A retained pixi view of the widget entities is therefore unit-testable without a renderer, better than today's spy-ctx tests.
4. Most other hand-rolled rendering code is already the right shape (native `NineSliceSprite`, `TilingSprite`, `ParticleContainer`, `BitmapText`/`BitmapFont`, `RenderTexture`, stock filters). The realistic "mainly removals" total for the whole project is about 340-420 source lines plus about 400 test lines, almost all in the UI stack (section 2). The user's expectation of large removals is only true if the Canvas2D UI path goes.

How @pixi/layout works (dist source read): importing it patches `Container.prototype` (mixins: `layout`, overrides `updateLocalTransform` on containers that have a layout, redefines the `visible` accessor) and registers a renderer system `layout` whose `prerender` runs `update(root)` every render when `autoUpdate` is true. `update` recurses over the ENTIRE scene under the render root, twice (`_updateSize` and `updateLayout`, core/LayoutSystem.mjs), so on a game stage with thousands of sprites it is pure per-frame overhead unless `renderer.layout.autoUpdate = false` and `update(uiRoot)` is called by hand. Styles: flex props plus `backgroundColor`, `borderColor`, `borderRadius`, `overflow`, `objectFit`, `%` sizes, `intrinsic` sizing for leaves.

## 3. Decision: UISystem + WidgetTree vs @pixi/layout + @pixi/ui

### 3.1 What each option would replace

Current: WidgetTree.ts 282 lines. Only lines 177-261 (about 85) are the yoga glue: ECS `LayoutStyle` to yoga node mapping (about 30), root `calculateLayout`, absolute-offset accumulation into `Layout`. The rest (WidgetParent relation, Hierarchy query ordering with its 3 documented bitECS gotchas, entity map, destroy) is ECS, and it is needed with or without pixi.

- Option L (@pixi/layout for layout only): each widget entity owns a `Container` with `layout={...}`; the tree lives in pixi; `LayoutSystem.update(uiRoot)` computes. Replaced: the 30-line style mapping (becomes a similar 30-line mapping to layout's vocabulary), the 55 lines of root calc and offset accumulation. Net about -50 lines, in exchange for an 800 KB dependency, global `Container.prototype` patching (including `visible`), a second tree (pixi parent/child) that must mirror `WidgetParent` and `Layout` output (two sources of truth, plus destroy ordering), and `autoUpdate=false` discipline. Also `WidgetTree.layout(scene, w, h)` has a pure-ECS contract that VNTextbox, DebugOverlaySystem, the IDE placement editor and their tests already rely on (packages/vn/src/**tests**/VNTextbox.test.ts, engine DebugOverlaySystem.test.ts, apps/ide/src/**tests**/uiPlacementLayout.test.ts, WidgetTree.test.ts 182 lines). Verdict: **skip**; the gain is smaller than the migration and adds global side effects. Keep yoga in WidgetTree. (Optional later: `flexWrap`, `%` sizes, `justifyContent`/`alignItems` are not in `LayoutStyle` today and cost about 4 lines each on the yoga side if a game needs them. That is not a reason to adopt a library.)
- Option U (@pixi/ui widgets): FancyButton/Slider/CheckBox/ProgressBar own their state (`progress`, `value`, `checked`) and fire `typed-signals` from federated pointer events. The ECS design (docs/decisions/ui-and-visual-scripting.md, "widget state lives on components") puts that state in `ButtonState`, `Slider`, `Checkbox`, `Progress` so it is polled, saved and scripted. Adopting @pixi/ui means two-way syncing every widget between ECS and library state, forwarding the engine's DOM PointerSystem coordinates through pixi's EventSystem (camera-independent GUI space, multitouch drags, engine-defined 6 px click threshold) and shipping 2 MB plus `tweedle.js` and `document`/`window` code inside packages/engine (which must not touch the DOM). Its five widgets in scope (panel, button, checkbox, slider, progress) are about 100 lines of Graphics code in a view. Verdict: **skip**, confirmed with a concrete cost. It may make sense in apps/ide for IDE chrome only if the IDE ever renders UI in pixi; not for the engine.
- Option V (recommended): keep ECS + WidgetTree/yoga as the data and layout model, replace only the Canvas2D **rendering** with a retained pixi view.

### 3.2 Option V, minimal design

New `packages/engine/src/ui/UIView.ts` (about 200-250 lines; name is a suggestion):

- Holds `Map<eid, {root: Container, bg: Graphics, label?: Text|BitmapText, img?: Sprite}>`, a `Container` root mounted on `RenderSystem.guiStage` (already camera-independent) or a dedicated UI container.
- `sync(scene)`: iterate `tree.orderedWidgets(scene)` (parent-before-child, so `addChild` order equals paint order), and for each entity set `root.position` from `Layout`, `root.visible`/`alpha` from `WidgetAppearance`, redraw `bg` only when the inputs changed (compare a cheap signature: box, colours, state, radius; skill pixijs-scene-graphics: "Clearing and redrawing Graphics every frame - HIGH"), update `label.text` only when changed (pixijs-scene-text: `.text` per frame is "High" for Text, "Very low" for BitmapText), destroy views for eids no longer present.
- Fonts: reuse `RenderPipeline._resolveBitmapFont` (RenderPipeline.ts:782-810 already installs a pixi `BitmapFont` from a `BitmapFontDef`) so `fontId` resolves to the same family as `draw_text`; CSS fallback uses `Text`. This deletes `_drawBitmapText`, the `drawImageRegion` glyph blit and its white-only tint restriction (BitmapText tints via `fill`).
- Images: `Sprite` from `TextureStore` (already shared with RenderPipeline); no `texture.source.resource` extraction.
- Slice-style panels could use `NineSliceSprite`, optional.
- Hit-testing, press/drag/click, hover stay in `UISystem` on `Layout` boxes (pure ECS, headless, no pixi events). This is the cheap part and it is what the tests and VN already use.

What is lost: the Canvas2D `IUIRenderer` seam and its spy-ctx tests (UISystem.test.ts 577 lines, about 350 of them render assertions), and the IDE placement panel's ability to render widgets straight into its 2D overlay canvas. Mitigation: the IDE panel is the only consumer; either mount a small pixi renderer in the panel (ShaderEditor.tsx:335 already does this) or keep `IUIRenderer` in apps/ide as a local preview adapter. Decision suggested: keep a thin 2D path in the IDE only if the panel cannot host pixi cheaply; otherwise delete it.

What is kept: all layout/hit-test/state tests headless, unchanged. New render tests assert on the view tree in Node (child counts, `Text.text`, `Graphics` instruction data, positions), which works without any renderer (verified constructors). Real pixels remain a GPU check (add to gpu_followup, replacing the existing "UISystem bitmap-font text never seen on a real Canvas2D surface" item, which then disappears).

Engine boundary rule: pixi.js is already an approved dependency (docs/decisions/engine-core.md lines 3-7), UIView adds no new dependency and no DOM. A single-line justification under engine-core.md is only needed if @pixi/layout or @pixi/ui were added; they would not be under option V.

## 5. Deviations from pixijs-skills (current working tree; file:line)

Status vs 03: D1 mostly mitigated (WGSL programs in CustomShaderFilter.ts:124-137 and a once-only warning `warnIfGlOnlyFilter` RenderSystem.ts:373), D2 (leak) and D3 (Text per draw_text) fixed via the pool (RenderPipeline.ts:115-196), D6 fixed (particle pool :883-918), D7 fixed for the renderer (`releaseGlobalResources: true` RenderSystem.ts:982). Still open:

- V1 MED. `preference: ["webgpu","webgl"]` at RenderSystem.ts:212 (and demo/BouncingBalls.ts:41) contradicts the doc comment at RenderPipeline.ts:922-928 that says WebGL is the default. pixijs-application: `preference: "webgl"` in the quick start; pixijs-filters: WebGPU needs `gpuProgram` on every filter. GLSL-only user shaders that fail the GLSL-to-WGSL conversion still render nothing on WebGPU. Make WebGL the default with WebGPU opt-in.
- V2 MED. No `boundsArea` on the particle `ParticleContainer` (RenderPipeline.ts:856-868); skill rates it HIGH once culling is enabled. Harmless today only because culling is not enabled.
- V3 MED. No render groups and no culling anywhere (grep: no `isRenderGroup`, `enableRenderGroup`, `cullable`, `Culler` in packages/engine/src). World `_stage` (RenderSystem.ts:~226) and tilemap containers (RenderPipeline.ts:1551) are plain containers. pixijs-scene-core-concepts/references/render-groups.md: use for "a game world / HUD / parallax"; "do not nest many". Measure first; add one group for the world stage and one for `guiStage`.
- V4 LOW. `Assets.unload`/`unloadBundle` never called (grep none); TextureStore.ts (:28-37) only loads. pixijs-assets "Not unloading textures between levels - HIGH". GC options (`gcMaxUnusedTime`, `gcFrequency`, `gcActive`) not set in `autoDetectRenderer` (RenderSystem.ts:205-216); pixijs-performance section on GC.
- V5 LOW. Per-frame `Text.text` for dynamic labels goes through the pool but `label.text !== text` guard exists (:331); skill compliant. BitmapText is only used when a GMS2 font is registered; other fonts use canvas `Text` (:344). Acceptable; dynamic `BitmapFont.install` would remove it.
- V6 LOW. Filters have no `filterArea` (RenderSystem.ts filter attach, RenderPipeline per-sprite shaders); per-sprite shader filters each cost an offscreen pass (04, 12).
- V7 LOW. Events/accessibility: the engine never sets `eventMode`, `hitArea`, `accessible` (grep none). That is consistent with its own DOM PointerSystem; the consequence is no screen-reader surface for the game. If UIView (section 3) lands, `accessible`/`accessibleTitle` on button views is nearly free (pixijs-accessibility: needs `eventMode = "static"` and the AccessibilitySystem, main thread only), which would be the first accessibility support the engine has. Optional.

## 6. Mixing Three.js behind d3d_* (guide read in full)

Guide facts: create the three `WebGLRenderer` with `stencil: true` (pixi masks need it), create pixi's `WebGLRenderer` and `await init({context: threeRenderer.getContext(), width, height, clearBeforeRender: false})`, per frame `threeRenderer.resetState(); threeRenderer.render(scene, camera); pixiRenderer.resetState(); pixiRenderer.render({container: stage})`, keep sizes in sync, textures/assets are not shared, order may be swapped or interleaved.

Structure for this engine:

1. New optional package `@emptysock/three` (peer dep `three`, MIT, current 0.186.x) exporting an `I3DBackend` implementation; interface `I3DBackend { init(canvasOptions): WebGL2RenderingContext; resize(w,h,dpr); render(scene3d: Scene3DSnapshot): void; loadModel(path): Promise<ModelHandle>; dispose() }` lives in `@emptysock/types`. The engine never imports three.
2. RenderSystem.init gains an optional `backend3d`: it creates the three renderer first, then `autoDetectRenderer({ preference: "webgl", context, clearBeforeRender: false, ... })` (forcing WebGL; a WebGPU pixi renderer cannot share a GL context). `useBackBuffer` for advanced blend modes must be re-verified on a shared context.
3. RenderPipeline.renderFrame: `backend3d.render(...)` then `renderer.resetState()` on both, then existing pixi passes. `d3d_*` GML calls (compat/gmlProjection.ts, `Projection3D` component, `PhysicsSystem3D` unaffected) write a `Scene3DSnapshot` (camera matrices from `Projection3D`, primitives from `d3d_draw_*`, models from `d3d_model_*`) instead of feeding `PerspectiveMesh`. The pixi 2D layers become overlay.
4. Not in scope of the guide but required: GLTF/OBJ loader for `d3d_model_*` (three has them), texture upload duplicates (separate pipelines), multi-camera and surface render targets (three renders only to the shared default framebuffer unless `WebGLRenderTarget` is bridged), GML depth/fog/lighting semantics, WebGL-only, never runs headless.

Effort: spike (context sharing, camera from `Projection3D`, a cube and one glTF) 3-4 days; parity with existing `d3d_*` surface, surfaces, multi-camera, resize/dpr, HMR/teardown (`releaseGlobalResources` on both) 3-5 weeks; plus a real-GPU test rig the project does not have (gpu_followup shows only swiftshader). Recommendation: **do not build now.** The current `PerspectiveMesh` path is deliberately a 2.5D fake and covers the compat surface; real 3D adds an optional package, WebGL lock-in, and unverifiable-headless code before the existing GPU verification backlog is cleared. Revisit when a target game needs real models. Capture the design above (no code) in docs/decisions/rendering-and-pipeline.md when doing the docs step.
