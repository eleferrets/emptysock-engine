# 03 - Pixi ecosystem audit (research pass item 3)

Read-only audit, 2026-09-29, branch sweep/housekeeping-research. Nothing installed or changed. Sources: pixijs/pixijs-skills (MIT, last push 2026-09-17; performance, application, ticker, filters, particle-container, bitmap-text SKILL files read; others skimmed via index), npm registry, GitHub API, pixijs.com "Mixing Three.js and PixiJS" guide. The pixijs.com ecosystem page URL 404ed under the 8.x guide tree; library facts below come from npm and GitHub instead.

## 1. Versions and API

- pixi.js `^8.21.0` via pnpm catalog (pnpm-workspace.yaml); lockfile resolves 8.21.0 (npm latest 8.21.0, 2026-09-17). API in use is v8 (async init, `Graphics.rect().fill()`, `ParticleContainer`+`Particle`, `Filter({glProgram,resources})`). No v7 leftovers found.
- Declared in: packages/engine (`pixi.js`, `pixi-filters ^6.1.5`, `yoga-layout ^3.2.1`), packages/tilemap (`pixi.js` - declared but src has no pixi import except one test, likely unused dep), apps/ide (`pixi.js`).
- The engine "no DOM, only stdlib and @emptysock/*" rule is already loose in practice: engine depends on pixi.js, pixi-filters, yoga-layout, bitecs. Any new dependency below is therefore a policy decision, not a fresh violation. `RenderSystem.init` touches `window.devicePixelRatio` behind a `typeof window` guard (RenderSystem.ts:184) and reads `renderer.canvas` (:197) - the only DOM contact.
- Design fact that shapes everything: the engine does NOT use `Application`/`Ticker`. It calls `autoDetectRenderer` (RenderSystem.ts:189) and `renderer.render(root)` (:896); the host drives the loop. This is the pixijs-skills-sanctioned `autoStart:false` shape and is correct; do not "fix" it.

## 3. Deviations from pixijs-skills (file:line)

Ranked by severity.

- D1 HIGH, WebGPU-first with WebGL-only filters. RenderSystem.ts:207 `preference: ["webgpu","webgl"]`, but `CustomShaderFilter.ts:97` and `RainGlassFilter.ts:204` build filters with `GlProgram.from` only, no `GpuProgram`. pixijs-filters SKILL: "Omitting one skips that renderer", so on any WebGPU-capable browser GML `shader_set` filters and rain glass silently do nothing. The doc comment at RenderPipeline.ts:833-843 says WebGL is the default ("§18 audit: prefer WebGL for production") which contradicts the code. All GPU verification so far used swiftshader/WebGL (gpu_followup). Fix: default to `preference: "webgl"` (matches the comment and pixi guidance) with WebGPU opt-in via `RenderSystemOptions`; keep `useBackBuffer:true` (:210, WebGPU always enables it anyway). BouncingBalls.ts:43 demo has the same preference; harmless (no filters).
- D2 HIGH, leak in immediate-mode GML draw. `PixiGmlDrawTarget` constructor clears with `graphics.clear(); graphics.removeChildren()` (RenderPipeline.ts:133-134, again :176-177) every dispatch. `removeChildren()` does not destroy, so every prior frame's `Text`/`BitmapText`/`Sprite`/blend-segment `Graphics` children (created at :152, :263, :271) are dropped un-destroyed; their canvas textures live until pixi GC (60 s default). Fix: destroy or pool them (`for (const c of graphics.removeChildren()) c.destroy()`), or keep a per-target text pool keyed by call index.
- D3 HIGH (perf), canvas `Text` created per `draw_text` per frame: RenderPipeline.ts:271. pixijs-performance: "Updating Text every frame - HIGH; use BitmapText / guard on change". Route the fallback through dynamic `BitmapText` and pool nodes (verdict row above).
- D4 MED, no culling anywhere. grep for `cullable`, `cullArea`, `Culler`, `CullerPlugin`, `cullableChildren`: none. Tilemaps (:1496) and room-scale layers render everything. Camera is a stage transform (CameraSystem writes to `stage`), so a cheap approach without the plugin: `Culler.shared.cull(stage, screenRect)` manually before `render` in RenderSystem.ts:~891, with `cullable` on tile containers / big sprites and `cullableChildren=false` on `guiStage`. Only worth it when GPU-bound; profile first.
- D5 MED, no render groups. Layer containers are plain `Container` (RenderSystem.ts:252 `_rebuildLayerContainers`, :276-283). The skill says static, rarely-changing subtrees (tilemap layer, parallax backgrounds) should be `isRenderGroup: true` (or `cacheAsTexture`) so camera pan is a GPU uniform, not a transform walk. Set `isRenderGroup` on the world `_stage` (RenderSystem.ts:~206) and on tilemap containers (RenderPipeline.ts:1425).
- D6 MED, particle churn. `_syncParticles` (RenderPipeline.ts:808-832) does `removeParticles()` then `new Particle({...})` for every live particle every frame - GC pressure and per-call view updates (skill: "batch via particleChildren + one update()"). Fix: keep a `Particle[]` pool per container, mutate fields, and set `particleChildren.length`; `dynamicProperties` are set right (:782-787). Also add `boundsArea` (skill HIGH: "empty bounds default, container culled/hit-test misses once culling is on"); currently absent at :781.
- D7 MED, no destroy of global pools on teardown. `RenderSystem.destroy` calls `this._renderer?.destroy()` (RenderSystem.ts:940), ShaderEditor.tsx:396 `rendererRef.current?.destroy()`, BouncingBalls.ts:148 `app?.destroy()`. Skill CRITICAL: without `{ releaseGlobalResources: true }` pooled batches/textures leak into the next renderer (flicker on IDE preview restart, headless GPU tests, HMR). Pass it in all three.
- D8 LOW, `Assets` is used correctly (TextureStore.ts:28-37 `Assets.load` / `Assets.cache` / `Assets.get`) but nothing ever calls `Assets.unload` (grep: none), so scene changes never free GPU textures; only pixi's GC (defaults, no `gcMaxUnusedTime`/`gcFrequency` set) reclaims them. Add `Assets.unload` (or `texture.destroy(true)`) on scene unload for scene-owned paths; consider tuning `gcMaxUnusedTime` via `autoDetectRenderer` options.
- D9 LOW, filters: no `filterArea` set (RenderSystem.ts:356, RenderPipeline.ts:238/1345). Per-sprite shader filters (RenderPipeline.ts:238, :1345) cost an offscreen pass each; research item 4 (Mesh+Shader) remains the real fix. Set `filterArea` where bounds are known, and `filters = null` on removal (already done at :1335).
- D10 LOW, graphics API: v8 chain style used correctly (`rect().fill()`, `stroke()` at :245-263); the GML segment-per-blend-mode `Graphics` (:152) is the only batch-break source and is inherent to the GML semantics.
- D11 INFO, `sortableChildren = true` (RenderPipeline.ts:1070, :1509, :1519) is v8-valid; keep.
- D12 INFO, ticker: not used by engine; the only `app.ticker` use is BouncingBalls.ts:52 (correct v8 callback shape with `ticker.deltaTime/deltaMS`).
- D13 INFO, tilemap package declares `pixi.js` (packages/tilemap/package.json:26) but has no runtime pixi import (its comment says "no pixi"): move to devDependencies or drop.

## 4. Engine-rule conflicts to flag

- Adding `@pixi/tilemap`, `@pixi/ui`, `@pixi/layout` to packages/engine means new runtime deps under the "stdlib and @emptysock/*" rule; pixi.js/yoga already breach it literally, so the decision needs a line in docs/decisions/conventions-and-process.md, not silence.
- `pixi-viewport` and `@pixi/ui` bind DOM pointer/wheel events (federated events); they can live only in apps/ide, never in packages/engine.
- Three.js must not enter engine at all (section 5).

## 5. Mixing Three.js behind the `d3d_*` compat

Guide facts (pixijs.com 8.x "Mixing Three.js and PixiJS"): create the three `WebGLRenderer` with `stencil: true` (needed for pixi masks); create `new WebGLRenderer()` from pixi and `await init({ context: threeRenderer.getContext(), width, height, clearBeforeRender: false })`; per frame: `threeRenderer.resetState(); threeRenderer.render(scene,camera); pixiRenderer.resetState(); pixiRenderer.render({container: stage})`. Keep sizes in sync; resources are not shared between libraries.

Fit with the engine: today `d3d_*` is a 2.5D fake - `PerspectiveMesh` per Transform+Sprite entity (RenderPipeline.ts:1158-1390, compat/gmlProjection.ts 338 lines) and PhysicsSystem3D. pixijs-skills is explicit: PerspectiveMesh "is not true 3D" (scene-mesh SKILL:41-51: "true 3D -> use a dedicated 3D library"). Recommendation: adopt later, as an optional package (`@emptysock/three`, three as peer dep, MIT) that the host injects through a new `I3DBackend` interface in @emptysock/types; RenderPipeline calls it before the pixi pass. Constraints: forces WebGL (so D1 fix is a prerequisite - and the pixi renderer must be created from the three context, meaning RenderSystem.init needs a `context` option); `resetState()` on both sides every frame; `d3d_model_*` GML loaders would need a glTF/OBJ path; surfaces/`bm_*` back-buffer features (`useBackBuffer`) interplay unverified; never runs headless. Do not start before the GPU verification backlog (gpu_followup) is cleared.

## 7. Risks

- D1/D5/D6/D7 change GPU behaviour that has only been verified under swiftshader; regress silently without a real-GPU pass (gpu_followup list).
- Render groups (step 6) alter transform/filter/mask semantics for children and interact with the `_multiCameraCompositor` and surface backends (RenderSystem.ts:823, RenderPipeline.ts:462-490 render to targets).
- Dynamic BitmapText glyph atlases grow with distinct chars/styles; big CJK text needs an explicit `chars` cap or MSDF via AssetPack.
- @pixi/tilemap and pixi-viewport are lightly maintained (last releases 2025-07 and 2024-11); if ever adopted, pin exact versions and wrap behind an interface.
- Three.js path would tie `d3d_*` to WebGL and to a shared GL context; cannot be verified headlessly; keep as an opt-in package.
- Facts not verified: the pixijs.com ecosystem page (URL 404ed), and the exact WebGPU failure mode of a Filter with no `gpuProgram` (skill text says the renderer is skipped; confirm on a real WebGPU browser before step 1 lands).
