### Scene transitions: `SceneTransitionManager` times them, `RenderPipeline` paints them

`SceneTransitionManager` (`systems/SceneTransition.ts`) takes an `effect: TransitionEffect` but never imports pixi — it stays inside the engine environment boundary (Node/browser/Tauri all run it). It drives a minimal `TransitionEffectSink` interface (`beginTransition`/`transitionProgress`/`endTransition`) via `attachPostProcess()`; `PostProcessSystem` satisfies that shape structurally. Actual pixels come from `RenderPipeline.renderTransitionOverlay(postProcess)`, which reads `PostProcessSystem`'s `transitionEffect`/`transitionProgress`/`transitionColour` and draws a full-screen `Graphics` rect — a triangle wave for `fade`, a growing rect for `wipe`, a rect sweeping across the screen for `slide`. This is an overlay-based transition (one rect on top of whatever's currently rendered), not a true two-scene crossfade — `RenderPipeline` doesn't keep two scenes' sprites live simultaneously.

A true two-scene crossfade is technically buildable (`renderer.render({ target: renderTexture, container })`, pixi v8's real object-form API) but its actual cost (a genuine two-full-render-pass-per-frame hit during the transition window) has no documented number from pixi's own docs and can only really be judged by profiling real target devices, including lower-end tablets — not something a headless CI sandbox can do. Shipping an unvalidated perf-risk rendering path without being able to verify it would be worse than keeping the overlay approach, which is proven and cheap. Revisit only once real device profiling is actually possible.

`SceneTransitionManager` is not a singleton — game code constructs its own `new SceneTransitionManager()`. It also owns no scene registration or pause/resume stack: `Game.ts` already owns scene swapping (`loadScene()`/`loadOverlay()`/`unloadScene()`) with its own lifecycle guarantees, so `SceneTransitionManager`'s only job is timing a transition's visual progress and calling a caller-supplied `load` callback once the duration elapses.

### SaveSystem storage backend is an injected adapter, not a runtime check

`SaveSystem` needs one save/load API that ends up on IndexedDB in the browser preview and Tauri's fs plugin on desktop, but unlike the "Tauri detection at runtime" pattern elsewhere in this file, `SaveSystem` does **not** check `'__TAURI_INTERNALS__' in window` itself — doing so would still require importing (even dynamically) an IndexedDB or `@tauri-apps/plugin-fs` code path from inside `@emptysock/engine`, which is exactly what "Engine environment boundary" forbids. See "Transport and StorageAdapter are interfaces" above.

Separately, `ComponentDef` carries a `version: number` (default `1`, set via `defineComponent(name, defaults, { version })`'s optional third argument). `SaveSystem` stamps every saved component instance with its def's version; on load, a stamped version that doesn't match the currently-registered def's version runs a migration registered via `SaveSystem.registerMigration(componentName, migrate)`, or — if none is registered — logs a warning and drops just that one component's data for that one entity. Everything else in the save still loads; a schema mismatch on one component type never aborts or corrupts the rest of the load.

### GMS2 `persistent` instances: `Meta.persistent`, snapshot in `onUnload`, restore in the next room's `onLoad`

Real schema (a real project): the per-object `.yy` has `"persistent": true`; room `.yy` instances carry NO per-instance persistent flag, and a room's own `roomSettings.persistent` is a different, unimplemented concept (whole-room state). Persistent objects there: `obj_display_manager`, `obj_game`, `obj_input`, `obj_sidebars`, `obj_trans`, `obj_transition` (obj_camera is not). Flow: `rm_init` (places `obj_display_manager`, whose Step runs `room_goto(rm_init2)`) -> `rm_init2` (places obj_game/obj_input/obj_trans/obj_camera/obj_sidebars) -> gameplay rooms (`rm_1`, ...) which place none of them, so the controllers only exist through persistence.

Importer: `buildObjectPrefabJSON` merges `solid` and `persistent` into ONE `Meta` override entry (`Meta.persistent`, `Serializable` boolean, default `false`, in the schema). `GmsProjectRuntime.buildSceneDefinition()` adds `onUnload` -> `snapshotPersistent(scene)`: for each `Meta.persistent` entity, copies every component the `componentRegistry` has seen on that world (fields shallow-copied, `bodyHandle` nulled so the new `PhysicsSystem` recreates it), plus `exportGmlVars` (instance vars), `exportGmlActionState` (motion/alarms/`xstart`/`ystart`; `gmlStatics` is process-global, nothing to do), then clears the old `(world, eid)` side-tables. `onUnload` runs synchronously inside `Game.loadScene()`, so it covers `loadRoom()` and the `ctx.rooms` path (`action_next_room`/`room_goto`) identically. The next room's `onLoad` calls `restorePersistent()` BEFORE `loadSceneFile()`: `scene.spawn()` + `entity.add` per component (same `Meta.name`), side-tables re-imported, no `onCreate`/`onSpawned`. Instance vars holding an `Entity` of a carried instance are remapped to its new entity; refs to non-persistent (now gone) instances become `undefined`.

No de-dupe, deliberately: GameMaker does NOT skip a destination room's own placement of an already-persisting object; it creates a second instance (the known duplicate-controller pitfall; manual.gamemaker.io Object Events/Room Properties, Bugnet "Persistent Room Doubles Instances"), and Create runs only once per instance lifetime. We match that; tests assert two instances. Tests: `GmsRuntime.test.ts` "persistent instances" block; the playability smoke test. Note `packages/toolchain` tests import `@emptysock/engine` from gitignored `packages/engine/dist` — rebuild (`tsc -p tsconfig.json`) after engine changes.


### Unified scene shape: `SceneDocument`, `formatVersion: 2`

One on-disk `.scene.json` shape now serves the IDE room editor, the GMS2 importer and the runtime loader; it replaces both the never-produced `EntitySchema`/`SceneSchema` (`@emptysock/types`) and the runtime `SceneFile`. Research and rationale: `docs/research/13-unified-scene-shape.md`. Sources of truth: zod `SceneDocumentSchema` in `packages/types/src/scene.ts`; zod-free structural interfaces in `packages/engine/src/SceneDocument.ts` (the engine cannot import zod); validation/migration in `packages/engine/src/SceneMigrations.ts` (`migrateScene`, `parseSceneDocument`). Shape: one flat `entities` array where a prefab instance and a plain entity are the same record (`{ id, name?, tags?, active?, parent?, persistent?, prefab?: { name, props? }, components?: { <ComponentName>: { v?, data } }, layer?, pool?, ext? }`); `room: { width, height, viewsEnabled?, views?, layers? }`; scene-level `persistent?` (GMS `roomSettings.persistent`, now emitted by the importer but not yet acted on at runtime; the object-level carry-over above is unchanged); `component.data` are overrides over the component's defaults; `ext.gml.vars` holds GameMaker instance-variable overrides (was `gmlVars`). Hierarchy is by `parent` id, validated (existing, acyclic) but inert at runtime until the entity-relation work lands. `loadSceneFile` spawns in array order, applies `prefab.props` then per-component overrides, and mirrors `name`/`tags`/`active`/`persistent` onto `Meta`.

Rule: readers accept every older version, writers emit only the latest, no dual-write. A file without `formatVersion` is v1 (the old `SceneFile`) and is migrated on read by `migrateScene` (`prefabInstances[i]` -> entity `p<i>`, `entities[j]` -> `e<j>`, order preserved: prefab instances first, then direct entities; `sceneName` -> `name`; `roomWidth/Height/viewsEnabled/views` -> `room`, view ids `v<i>`; unknown top-level keys kept). A never-produced v0 editor tree (`children`, `components[{type,data}]`) is flattened best-effort. A newer `formatVersion` than supported is a hard error naming both versions. Producers (`gms2-room-import.ts`/`gms2-codegen.ts`/`gms2-import.ts`, IDE `roomEditorScene.ts`) write v2 only; importer entity ids are the placed instance's editor name when it is a valid id (so ids survive re-import), else `p<i>`, with `bg<i>`/`el<i>` for background and layer-element entities.

Decisions taken for the report's open questions (orchestrator defaults, this sweep):
- Ref ids are strings: an in-file reference is `{ "$ref": "<entity id>" }`, ids match `/^[A-Za-z0-9_-]{1,64}$/` (uuids allowed, not required); the numeric runtime `EntityRef` is a separate later concern. Structural refs (`parent`, `room.views[].follow.entity`) are validated now; component `entityRef` remapping is not implemented yet.
- `active` is kept: the engine already has real meaning for it, `Meta.active` (default `true`, read by `QueryChannel` for the IDE inspector), so the loader maps `active` onto it. (It does not disable the entity at runtime; nothing does today.)
- Prefab files (`*.prefab.json`, `PrefabFile`) are NOT migrated in this sweep; they keep the array `{component, overrides}` shape. Follow-up: move them to the same name-keyed `components` map with `v`.
- Component `v` (data version) is accepted and preserved but not yet consumed: no migration registry hookup on scene load.
- `layer` and `room.layers` are part of the shape (editor can list/reorder) but the loader does not act on them; `LayerElement` entities remain ordinary entities.
- Component order is the JSON key order of the `components` map (no separate `order` field); `SceneDocument.id` is optional and unused by the runtime.
- Schema location: `packages/types` (zod) is the validation source of truth with a structural engine copy; a shared-fixture drift test between the two is a follow-up (only a per-side test set exists today).

Not done in this sweep (next sweeps): `EntityRef` relation APIs and `$ref` remap on load, `SceneTransfer`/room-cache emitting `SceneEntity` (the private `byOldEid` map in `GmsRuntime` is unchanged), runtime use of `parent` and scene `persistent`, and the IDE hierarchy view (`EntityItem`/`SceneInspector`) deriving from `parent`.


### Scene transfer, `Game.loadScene({ carry })`, persistent rooms, globals, save v2

Implements steps 1-4, 6, 7, 9 of `docs/research/07-persistence.md` (step 5, the importer, already emits `persistent`; step 8 is IDE/types and untouched).

**GameMaker semantics verified against the manual (fetched this session):**
- Room Properties, "Persistent": "The room status will be remembered and when you return to it later, it will be exactly the same as you left it, with it only being reset to the start state when the game is restarted." Creation code "will run every time you enter the room, unless the room is flagged as persistent, in which case it will only be run once when the room is first entered". Objects flagged persistent do not stay in the room: "instances of this object will not stay in the room but move to the next room."
- `room_persistent`: state of the instances is maintained when leaving and returning; non-persistent rooms reset to initial state; a persistent room "uses considerably more memory".
- `game_restart` manual page: "Global Variables will not be re-initialised unless explicitly coded as such"; persistent objects are removed on restart (only objects persistent by definition are created again afterwards). **This contradicts the research report** (section 2 said `game_restart` resets globals). We follow the manual: `game_restart` does not touch `GlobalStore`; `GlobalStore.reset()` exists for games that want it explicitly.
- Not verified: exact behaviour of `room_restart` on a persistent room (we discard that room's cache entry, matching "restart re-creates the room"), and statics/module-level state on `game_restart` (still a documented gap).

**Design as built:**
- `SceneTransfer.ts` (core): `captureEntities`/`restoreEntities` with `TransferPolicy { select, extras, remap }`; `EntityExtra` carries state kept outside components (GML vars and motion are the first two, registered in `GmsRuntime.ts`; core never imports `compat/`). Restore respawns all entities, runs `remapRefs` on declared `entityRef` fields, then lets extras import with `ctx.remap` (shared `remapValue`: source-scene `Entity` handles and `$ref`s; references to non-carried entities become `undefined`/`NO_REF`). Old identity is `Scene.idOf`, so research step 3 (id-map) was done in the same commit as step 1. `ComponentDef.transfer` lets a component reset engine-managed state (`PhysicsBody` nulls both Rapier handles; previously only `bodyHandle`).
- `Game.loadScene(def, { carry })` captures after the outgoing `onUnload`; the new scene calls `ctx.restoreCarried()` explicitly (first thing in `onLoad`). `Game.loadScene` `restart: "room" | "game"` and `Game.restarting` back `room_restart`/`game_restart`.
- `SceneDefinition.persistentKey` + `Game.roomCache` (`RoomStateCache`): leaving a keyed scene caches every entity that is not object-persistent; `ctx.restoreRoom()` in `onLoad` consumes the entry and the scene skips its own population (no Create rerun). Object-persistent entities travel and are not cached; order is carried first, then room.
- `GlobalStore.declare/declared/snapshot/restore/reset`: only `persist: true` names snapshot; non-JSON values are dropped with a warning; `restore` ignores undeclared names with a warning.
- `SaveSystem`: the blob was already `formatVersion: 2` (ids + relations) before this work, so v2 was extended additively instead of introducing a v3: optional `meta`, `room`, `globals`, `variables`. `load` now checks `formatVersion`: a newer version throws `SaveFormatError` before touching anything, no/older version loads (v1 needs no rewrite). `load` defaults to `mode: "replace"` (destroys live entities carrying save-aware components first); `"append"` keeps the old behaviour. Entities are written sorted by id. `peek(slot)` reads the header.

**Not done / known gaps:** the room cache and in-flight carry are not written into save files (extras hold non-JSON state such as GML `Map`s and entity handles); `SaveSlotSchema` in `packages/types` and the IDE globals declaration shape (step 8) are unchanged; no `EntityExtra.version`/globals-migration hook; `gmlStatics` and module-level game state survive `game_restart`; cached-room entities referencing carried ones (or the reverse) dangle to `NO_REF`/`undefined`.
