### GameMaker's "hypothetical position" collision-query family (`place_meeting`/`place_free`/`collision_*`)

GameMaker's classic solid-wall collision technique — call `place_meeting(x, y, obj)` at a _hypothetical_ next position before actually moving there, and back off if it would overlap something — is THE mechanism a huge fraction of real GameMaker platformers/top-down games use, and it's a real, implemented compat family now: `compat/gmlCollisionQueries.ts`, a sibling to `gmlActions.ts` rather than an extension of it (every function here is still entity-affecting — the calling instance's own mask matters — so it keeps the same `(entity, ctx, ...gmlArgs)` signature `gmlActions.ts` established, but this is a pure-query family with nothing to nest or dispatch, a different shape from `GmlCollision.ts`'s event-dispatch focus).

None of these move the calling instance — the "hypothetical" half of the semantic is real: `place_meeting(entity, ctx, x, y, obj)` reads `entity`'s current sprite-derived half-extents but never writes its `Transform`, checking the AABB overlap as if `entity` were already at `(x, y)`. `place_snapped(entity, ctx, hsnap, vsnap)` is the one exception with no scene query at all — GameMaker's own real signature has no `x`/`y`, it always checks the instance's _current_ position.

What's implemented:

- **`place_meeting`/`place_free`/`place_snapped`** — whole-mask checks against `entity`'s own hypothetical extents. `place_meeting` matches a named object type (or `all`/`noone`); `place_free` matches any `Meta.solid`-flagged instance instead (see below), independent of object type.
- **`position_meeting`/`position_free`/`instance_place`/`instance_position`** — the single-_point_ variants (no `entity` mask involved at all) plus the "return the actual instance, not just a bool" variants, matching GameMaker's own naming split. `instance_place`/`instance_position` return `Entity | undefined` — `undefined` standing in for GameMaker's `noone`, since there's no numeric "no instance" sentinel in this engine's `Entity` API.
- **`collision_rectangle`/`collision_circle`/`collision_line`/`collision_point`** — the general arbitrary-shape-vs-object-type family, each taking `prec` (always a no-op — no per-pixel mask data exists anywhere in this engine, honestly falling back to bbox checking, the same precedent `action_if_collision` already established) and `notme` (excludes the calling instance when `true`, GameMaker's own default).

**Object-type resolution** reuses `systems/GmlCollision.ts`'s `resolveGmlObjectType` (keyed off `Meta.name`) so this file and `onCollideWith<Type>` dispatch can never disagree about what an object-name argument resolves to. `all` matches every instance; `noone` matches nothing — GameMaker's own two special object-reference constants, checked by string equality before falling back to name resolution.

**This is not GameMaker's Box2D-based physics engine, and never should be treated as one.** Every function in this family is a synchronous bbox-vs-bbox geometry check against `Transform`/`spriteHalfExtents`, run once when called — there is no simulated world, no mass/velocity/restitution, no continuous integration, and nothing here talks to Rapier. GameMaker's real physics is a _separate, opt-in_ system (`physics_world_create`, `physics_fixture_create`/`_add_*_shape`, `physics_apply_force`/`_impulse`, `physics_joint_*`, a body's `phy_*` instance variables) that a GML project must explicitly turn on per-room — `place_meeting`/`place_free`/`collision_*` work identically whether or not a project ever calls `physics_world_create` at all, exactly like they do in real, non-physics GameMaker games. Confirmed: this codebase has **zero** compat wiring for the `physics_*`/`phy_*` family anywhere — not in `compat/`, not in `gms2-transpile.ts`. This is a real, deliberate, honest gap rather than an oversight: `PhysicsBody`/`PhysicsSystem` (Rapier-backed, see "PhysicsSystem3D must be destroyed" above) is this engine's actual real-physics answer, and a GMS2 project that never calls a `physics_*` function has nothing to import — building a full Box2D-semantics compat layer speculatively, with no real project exercising it, would be exactly the kind of unvalidated, unmodelled surface this file's other honest-gap entries (`action_if_question`, `image_index`/`image_speed`) already warn against. If a real project that actually uses GML's opt-in physics ever needs importing, that's the moment to design a `physics_*` → `PhysicsBody`/`PhysicsSystem` mapping — not before.

**`Meta.solid`** — GameMaker objects carry a real per-object "Solid" checkbox (`.yy`'s `solid` field), independent of whether the object also has a `PhysicsBody` — a classic non-physics GML game's solid walls are just solid-flagged instances, not physics bodies. `Meta` (already the one component `onCollideWith<Type>` dispatch and the Inspector both read for per-instance identity) gained a `solid: boolean` field for `place_free`/`position_free` to check against. `gms2-codegen.ts`'s `buildObjectPrefabJSON` reads the object's real `.yy` `solid` field and emits a `Meta` component override (`{ solid: true }`) when it's `true` — additive, the same "only emit when it actually differs from the default" shape the existing `physicsObject`/`spriteId` overrides already use.

**Transpiler wiring**: unlike GM8.1's DnD actions (always their own statement, always followed by `;`), this family is real GML _expression_ syntax — just as commonly called inside `if (...)`, a `&&` chain, or an assignment's right-hand side, with no trailing `;` of its own. `gms2-transpile.ts`'s `THREADED_ACTIONS` rewrite pass used to unconditionally append a semicolon after every rewritten call (safe for DnD's always-a-statement shape); that would have corrupted `if (place_meeting(...))` into `if (GmlActions.place_meeting(...);)`. The pass now captures the trailing `;` (if any) instead of assuming one, and echoes back exactly what was there — fixing this family without changing DnD's existing always-`;` behaviour at all. These functions are threaded the same `THREADED_ACTIONS` list DnD actions use, not a second rewrite pass — `if place_meeting(x + 4, y, obj_wall) { ... }` (already unwrapped to `if (place_meeting(...)) { ... }` by an earlier bare-condition pass) becomes `if (GmlActions.place_meeting(_entity, _ctx, x + 4, y, obj_wall)) { ... }`.

### GML behavior dispatch: three Step passes, a Collision pass, a separate Draw GUI pass

The GMS2 DnD action-library compat entry above covers what a transpiled action call _does_; this entry covers what actually _calls_ a GMS2-imported prefab instance's generated `onCreate`/`onStepBegin`/`onUpdate`/`onStepEnd`/`onCollideWith<Other>`/`onDraw`/`onDrawGui`/`onDestroy` functions in the first place — previously nothing did (and `onCollideWith<Other>` in particular stayed dead code even after the Step/Draw passes landed, since most GMS2-imported objects are plain `Transform`+`Sprite` with no `PhysicsBody` for `PhysicsSystem`'s own, unrelated `onCollisionEnter` side-table callback to ever fire against), per the "GMS2 import emits prefab/scene JSON..." entry's own "wiring these functions up to real prefab instances ... is left to the game" caveat.

`components/GmlBehavior.ts`'s `GmlBehaviorState` (`{ behaviorId: string }`) and `registerGmlBehavior`/`getGmlBehavior` registry are `VisualScriptState`'s exact shape, reused rather than reinvented: a generated `.behavior.ts` module's exports are real, static, imported code (not authorable at runtime the way a `VisualScriptGraph` is), so the game registers the module once under an id and many entities can reference the same id.

**Why `GmlBehaviorSystem.update()` is three full Step passes, not one interleaved pass.** GameMaker's real per-frame semantics (confirmed against GameMaker's own manual's Event Order page and community documentation of its event order) is: every instance's Begin Step event completes before any instance's Step event begins; every instance's Step completes before any instance's End Step begins. A single pass calling `onStepBegin`/`onUpdate`/`onStepEnd` back-to-back per entity would let entity B's Begin Step observe entity A's _this-frame_ Step write — GameMaker's own engine never allows that, because it finishes an entire event category across every instance before starting the next category. `update(scene, dt, ctx)` is therefore three separate `scene.each()` sweeps over every `GmlBehaviorState` entity, each one fully completed before the next starts: this is the only way to give the "no instance's Begin Step ever observes a Step write from the same frame" guarantee GameMaker's own instances rely on. `GmlBehaviorSystem.test.ts`'s cross-entity ordering test is a real behavioral proof of this, not just "no exception thrown" — it fails under a naive interleaved implementation.

**A real 4th pass, after Step and before Draw: Collision.** `update()`'s `resolveCollisions()` runs once, after the three Step passes, matching GameMaker's own event order (Step family completes, then Collision, then Draw). GameMaker's real default (non-physics) instance collision model is plain bounding-box overlap checked every step, firing each instance's Collision event specific to the _other_ instance's object type — an object can declare separate `Collision_A`/`Collision_B` handlers, independently triggered only by overlap with that specific type, never every Collision handler the entity has. `systems/GmlCollision.ts` holds the shared matching logic (`resolveGmlObjectType`/`checkGmlAabbOverlap`/`dispatchGmlCollision`) so it has exactly one implementation, not two that could drift: "object type" is resolved via `Meta.name` (the engine's one existing "editor/tooling-visible name" component — see the `QueryChannel`/`Meta.name`/`Meta.tags` entry below), which `SceneFile.ts`'s `loadSceneFile()` now stamps onto a spawned prefab instance from its `PrefabDef.prefabName` whenever nothing already set one, specifically so a GMS2-imported room's prefab instances resolve back to their GameMaker object name here; AABB extents reuse `compat/gmlActions.ts`'s existing `spriteHalfExtents` fallback (`action_if_collision`'s own bbox source), so the two "is GML-A touching GML-B" checks in this engine can never disagree. `resolveCollisions()` is broad-phase-then-narrow-phase: every `GmlBehaviorState` entity is a potential collision _source_ (only a source needs a compiled module to dispatch through), every `Transform`-bearing entity is a potential _target_ (a target needs no `GmlBehaviorState` of its own — GameMaker's own Collision event can be triggered by any instance), and `checkGmlAabbOverlap` is the actual narrow-phase test per pair.

A `physicsObject: true` GMS2 object still has a real Collision event in GameMaker even though it also gets a `PhysicsBody`, so `PhysicsSystem` optionally dispatches the same GML handler on a genuine Rapier contact: `attachGmlDispatch(ctx)` opts a `PhysicsSystem` instance into calling `dispatchGmlCollision` (both directions) from `_drainCollisionEvents` on collision-start, reusing the exact same `GmlCollision.ts` matching helper rather than a second, physics-flavoured copy of it. Unset (the default), a physics contact never touches GML dispatch at all — `PhysicsSystem` otherwise has no GML concept and must not require one to function, the same "engine defines the interface, whoever has a live instance wires the concrete implementation" pattern `StorageAdapter` already uses.

**Why Draw GUI's camera-independence is a render-tree structural property, not a per-call check.** `RenderSystem` gained a `guiStage` container that is a _sibling_ of `stage` (the container `CameraSystem.attach()` transforms), never a descendant of it — both are children of a new, internal-only `_root` container that's the actual thing passed to `renderer.render()`. `CameraSystem` only ever writes `stage.x`/`.y`/`.scale`/`.rotation`; a sibling container is structurally unreachable by that write no matter what the camera does. This is why `RenderPipeline._renderGmlDraw()` needs no camera-transform-reset logic at all — GameMaker's real "Draw GUI draws in screen space, Draw draws in world space" semantic falls out entirely from _where in the tree_ each draw target's `Graphics` is parented (`onDraw`'s into the `"foreground"` layer container, a descendant of `stage`; `onDrawGui`'s into `guiStage`), not from any runtime check in the dispatch code. `_renderGmlDraw()` is a genuine third pass in `renderFrame()` (after sprite sync and particle sync), not a conditional bolted into `_syncOne()`'s per-sprite loop — a per-sprite special case could not express "draw into a structurally different container tree" at all, since that method only ever writes into one sprite's already-assigned container.

**What `draw_*` actually draws into now.** `compat/gml.ts`'s `draw_set_colour`/`draw_rectangle`/`draw_circle`/`draw_text`/`draw_line` used to take a `CanvasRenderingContext2D` — a real, if unused, crack in the engine-environment-boundary rule (a DOM type reference, even if never actually wired to a live canvas). They now take a plain structural `GmlDrawTarget` interface instead. `RenderPipeline`'s new `PixiGmlDrawTarget` is the one real implementation: a pixi `Graphics` (vector shapes) plus `Text` children (pixi's `Graphics` has no text primitive of its own) for `draw_text`, rebuilt from scratch on every `onDraw`/`onDrawGui` call — the same "simplicity over per-frame allocation cost" tradeoff CLAUDE.md's own "ParticleEmitter renders through a real pixi ParticleContainer" entry already accepts. `GmlActionContext` gained an optional `drawTarget` field that `GmlBehaviorSystem.renderDraw()`/`renderDrawGui()` set only for the duration of one dispatch call each, so a `draw_*` call made from `onUpdate`/`onCreate` (outside a draw dispatch) sees `undefined` and no-ops honestly rather than drawing to a stale target.

**The real limits of this pass, stated honestly.** `Scene.spawn()`/`Scene.destroy()` do not call `onCreate`/`onDestroy` automatically — core `Scene`/`Entity` must not grow a required dependency on this optional compat layer, the same boundary `@emptysock/network`'s entity-mapping entry draws for its own optional add-on. `onCreate` dispatch's real integration point is `loadSceneFile()`'s new `onSpawned` option (called once per spawned entity, immediately after every component is attached and every prop applied) — a GMS2-imported room's `.scene.json` loaded through `loadSceneFile()` is exactly where a game wires `GmlBehaviorSystem.dispatchCreate()` in. `onDestroy` dispatch's real integration point is `GmlBehaviorSystem.destroy(scene, entity, ctx)` — the sanctioned way to destroy a `GmlBehaviorState` entity when its `onDestroy` handler matters, since `Scene.destroy()` itself has no `GmlActionContext` (no `Scene`/`Game`/`prefabs`/`rooms` map lives on the core `Scene` type) to dispatch one with. `action_kill_object` (GM8.1's "Destroy Instance") still calls `ctx.scene.destroy(entity)` directly and does not yet route through this — a real, separate follow-up for whoever wires GML behaviors into `action_kill_object`'s call sites next, not silently glossed over here.

`gms2-codegen.ts`'s event-file mapping now reads the real per-suffix `.gml` files GameMaker actually writes: `Step_1.gml`/`Step_0.gml`/`Step_2.gml` → `onStepBegin`/`onUpdate`/`onStepEnd` (GameMaker's own `ev_step_begin`/`ev_step_normal`/`ev_step_end` eventnum values — 1/0/2 — confirmed against GameMaker's manual's Event Order page), and `Draw_0.gml`/`Draw_64.gml` → `onDraw`/`onDrawGui` (`64` is GameMaker's long-standing `ev_draw_gui` eventnum constant). `onStepBegin`/`onStepEnd`/`onDrawGui` are emitted only when the corresponding `.gml` file actually exists — unlike `onCreate`/`onUpdate`/`onDraw`/`onDestroy`, which always emit a stub, these three are genuinely optional (`GmlBehaviorModule`'s fields are all optional, and `GmlBehaviorSystem` treats a missing export as "no handler for this pass", not an error), so emitting an empty stub for every object that never used Begin/End Step or Draw GUI would bloat every generated file for no reason. Draw Begin/End and Draw GUI Begin/End sub-variants are a real, separate, not-yet-covered gap.

### `GmsProjectRuntime`: the one place that actually drives a GMS2-imported project

Everything the two entries above document — `GmlBehaviorSystem`'s Step/Collision/Draw passes, `TimelineSystem`, `GmlSequenceSystem`, `gmlActionsStep`, `PhysicsSystem.attachGmlDispatch` — is real and callable, but until `packages/engine/src/GmsRuntime.ts` landed, nothing called all of them together, in the right order, against a live `Game`. `GmsProjectRuntime` is that orchestration: `new GmsProjectRuntime(game, data, options)` (constructed by the caller — a `GmsProjectRuntime` never constructs its own `Game`, the same "engine owns what it creates, but a `Game` is the caller's to construct" split every other engine entry point uses), `await runtime.loadRoom("room0")`, then `runtime.update(dt)` once per frame.

`GmsProjectData` (the constructor's second argument) is already-parsed, in-memory data — a room-name-keyed `Record<string, SceneFile>`, a `roomOrder` array, an object-name-keyed `Record<string, PrefabDef>`, a `ComponentLookup`, and an optional sound-id map — never a directory path or a file read. This mirrors `loadSceneFile`/`parsePrefabFile`'s own "engine takes already-loaded JSON, never reads files itself" shape (the engine-environment-boundary rule: no fs/DOM import in `packages/engine`). Building a `GmsProjectData` from a real GMS2-import output directory (reading every `.prefab.json`/`.scene.json`, parsing them, and — the genuinely host-specific part — importing/registering every generated `.behavior.ts` module via `registerGmlBehavior`) is left to the caller; a Node build imports `.behavior.ts` modules directly, a browser bundle needs them pre-bundled, and this class has no opinion on which.

`loadRoom(name)` builds one `SceneDefinition` per room (`buildSceneDefinition()`) whose `onLoad` calls `loadSceneFile()` with a real `onSpawned` hook — the exact integration point the "GML behavior dispatch" entry's "real limits of this pass" paragraph names — dispatching `GmlBehaviorSystem.dispatchCreate()` on every spawned entity that carries `GmlBehaviorState`, and whose `onUpdate` runs this class's own per-frame GML passes (`GmlBehaviorSystem.update()`, then `gmlActionsStep()` for every `GmlBehaviorState` entity, then `TimelineSystem.update()`, then `GmlSequenceSystem.update()`) before returning control to `Game.update()`'s own actor/physics/coroutine/render order. `runtime.update(dt)` itself is a thin forward to `game.update(dt)` — every GML-specific pass runs from the `onUpdate` hook `loadRoom()` already installed, not from a second, parallel update loop this class drives independently. This keeps `Game`'s own "the engine owns everything it creates" per-frame order as the one source of truth; `GmsProjectRuntime` adds a hook into it rather than reimplementing or racing it.

**Alarm dispatch is real, not just alarm-countdown.** `gms2-codegen.ts` names a generated alarm handler `onAlarm0`..`onAlarm11` per `Alarm_<n>.gml` source file (GameMaker has 12 alarm slots) — a real, confirmed shape (`gmlActionsStep`'s own doc comment says `gms2-codegen.ts` appends these specifically for its `onAlarm` callback parameter to call). Until this was wired, nothing ever passed that callback: `runGmlPasses()`'s `gmlActionsStep(entity)` call had no second argument, so `action_set_alarm`'s countdown still ticked but `onAlarm?.(index)` always resolved `undefined` and every real GameMaker Alarm event silently no-opped — a significant, previously-undiscovered gap, since Alarms are an extremely common GameMaker pattern (delayed actions, periodic behavior, state-machine timers). `runGmlPasses()` now passes a real closure — `(index) => this._behaviors.dispatchAlarm(entity, index, ctx)` — and `GmlBehaviorSystem.dispatchAlarm(entity, index, ctx)` is the real dispatch: it resolves the entity's compiled module via `GmlBehaviorState.behaviorId` (the same resolution every other `GmlBehaviorSystem` dispatch method already does) and looks up `onAlarm<index>` via `getGmlBehaviorHandler` — the same dynamic-lookup-by-name mechanism `onCollideWith<Other>` dispatch already uses, reused rather than reinvented, since a per-index handler name is generated per-project and can't be a fixed `GmlBehaviorModule` field. Routed through the same `safeCall` every other `GmlBehaviorSystem` dispatch method uses, so one entity's throwing `onAlarm` handler can't abort dispatch for any other entity, or any other alarm firing the same frame. A missing `GmlBehaviorState`, an unresolvable module, or an alarm index with no matching handler on the module are all safe no-ops — most real objects only ever arm a couple of the 12 possible slots.

**Key dispatch is real too, and — unlike Alarm — needed genuine up/down-transition tracking, not just a missing callback wire.** `gms2-codegen.ts`'s `buildKeyFns()` names a generated handler `onKeyPress<Name>`/`onKeyRelease<Name>` per `KeyPress_<vk>.gml`/`KeyRelease_<vk>.gml` source file (`vkNames`/`vkMethodName` map the common vk codes — 8/13/16/17/27/32/37-40 — to labels like `Space`/`Left`, anything else falls back to `Vk<code>`), and nothing ever called either one — confirmed by grep, zero references anywhere in `GmsRuntime.ts`/`GmlBehaviorSystem.ts` before this pass, the same class of previously-undiscovered gap the Alarm fix above found for a different event family. GameMaker's real semantic ("fires once on the frame a key transitions, not every frame it's held") has no existing engine-side primitive to hang onto the way Alarm's own internal countdown does — `InputManager` exposes `isDown`/`keyboard.isDown(code)` (a frozen-per-frame snapshot, see "Input snapshot: frozen by copy, not by timing" above) but no `justPressed`/`justReleased` of its own, so `GmsProjectRuntime` tracks the up/down transition itself: a single `Map<vkCode, boolean>` instance field (`_prevKeyDown`), polled once per frame in a new `dispatchKeyTransitions()` step that runs before `GmlBehaviorSystem.update()`'s Step passes. This is a plain instance field, not a `(World, eid)`-keyed side-table, because keyboard state is genuinely global — one physical keyboard, not per-entity state the way `PhysicsBody`'s callbacks or `VisualScriptState`'s evaluation scope are.

`compat/gmlKeys.ts` is the new home for two small, hand-kept-in-sync mirrors of `gms2-codegen.ts`'s own naming: `VK_NAMES`/`vkMethodName` (the exact same table, duplicated because `@emptysock/engine` cannot depend on `@emptysock/toolchain` — an offline-codegen CLI package, not a runtime dependency, the same boundary that keeps every other engine/tool pairing in this codebase one-directional) and `vkToDomCode` (a new translation this pass needed regardless: GameMaker's `vk_*` constants reuse the legacy numeric `KeyboardEvent.keyCode` numbering, but `InputSystem` tracks keys by the real DOM `KeyboardEvent.code` string, so a vk code has to be translated before it can be checked against `input.keyboard.isDown(...)` at all — a vk code with no known translation is honestly skipped, never guessed). `GmlBehaviorSystem.dispatchKeyPress`/`dispatchKeyRelease(entity, vkCode, ctx)` mirror `dispatchAlarm`'s exact shape: resolve the module via `GmlBehaviorState.behaviorId`, look up `vkMethodName(prefix, vkCode)` via `getGmlBehaviorHandler`, call through `safeCall`. `dispatchKeyTransitions()` computes the frame's pressed/released vk codes once (not once per entity — the transition itself is a single global fact) and offers them to every `GmlBehaviorState` entity, relying on the same "no handler for this name is a safe no-op" behavior `dispatchAlarm` already established for a missing alarm index, rather than inspecting which handlers each module actually exports first.

**Room transitions triggered from inside GML stay in sync with `runtime.currentRoom`.** `compat/gmlActions.ts`'s `action_next_room`/`action_another_room` call `ctx.game.loadScene(ctx.rooms[name])` directly — they have no reference to the `GmsProjectRuntime` instance that built `ctx`, by design (they're free functions callable with any `GmlActionContext`, not just one this class built). To keep `runtime.currentRoom` accurate even when a room change is driven this way rather than through `runtime.loadRoom()`/`runtime.nextRoom()`, `buildContext()` populates `ctx.rooms` with the exact same `SceneDefinition`s `buildSceneDefinition()` builds for `loadRoom()` — each one's own `onLoad` closure updates `this._currentRoom` — so a transpiled `action_next_room` call spawns entities, dispatches `onCreate`, and installs the per-frame GML passes exactly as if `runtime.loadRoom()` had been called, and `currentRoom`/`scene` stay correct afterward either way.

`options.camera`/`options.renderer` are optional live systems this class merges into one `GmsRuntimeContext` (`GmlActionContext & GmlCameraContext & GmlParticleContext` — the three compat files' context types are already structural supersets of the same base shape, confirmed by reading all three, so one merged object satisfies all three with no adapter needed: `gmlCamera.ts` and `gmlParticles.ts` both already spell their extra field `camera`/`particles` consistently with what `CameraSystem`/`RenderPipeline` actually are). When `options.renderer` is given, `loadRoom()` calls `RenderPipeline.attachGmlBehaviors(behaviors, ctx)` after each load, which is what makes `onDraw`/`onDrawGui` dispatch actually happen — that wiring already existed on `RenderPipeline` itself (`attachGmlBehaviors()`/`_renderGmlDraw()`), this class just calls it. With no renderer given, the runtime is fully headless: `update()` forwards to `game.update(dt)`, whose own render step (`Game`'s documented "no renderer attached" no-op) never runs, matching the rest of the engine's headless-testing story.

`destroyEntity(entity)` is the sanctioned way to destroy a `GmlBehaviorState`-carrying entity through this class — it calls `GmlBehaviorSystem.destroy(scene, entity, ctx)` (dispatches `onDestroy`, then the real `scene.destroy(entity)`), never a bare `scene.destroy(entity)`, for the same reason `GmlBehaviorSystem.destroy()`'s own doc comment gives: `Scene.destroy()` has no `GmlActionContext` to dispatch an `onDestroy` handler with.

**Honest gaps, not glossed over.** GameMaker objects do not declare a timeline/sequence on the object resource itself — confirmed against real `.yy` object files while researching this pass, a timeline is only ever assigned imperatively from GML (`timeline_index = tlFoo;`). `buildObjectPrefabJSON()` (`gms2-codegen.ts`) was deliberately _not_ changed to emit a fabricated static `TimelineState` link on a prefab — there is no such link in a real GameMaker project to codegen from, and inventing one would misrepresent GameMaker's actual semantics. `gms2-transpile.ts` now rewrites a bare `timeline_index = tlFoo;` assignment for real (manual.gamemaker.io's `timeline_index`/`timeline_running` reference pages, confirmed live for that pass): it quotes a bare asset-name identifier into the exact string `registerGmlTimeline()` already registers it under, and emits either `entity.add(TimelineState, { timelineId: "tlFoo", position: 0, running: true })` or a field write via `.get()` when the component is already present (re-targeting, since `Entity.add()` has one-shot semantics) — exactly the operation this paragraph used to describe as not-yet-wired. `timeline_index = -1` (GameMaker's own documented "no timeline" sentinel) rewrites to `entity.remove(TimelineState)`. `timeline_running`/`timeline_speed`/`timeline_loop`/`timeline_position` are rewritten on both the write and read side, straight onto `TimelineState`'s matching fields; a bare read of `timeline_index` itself is deliberately left unrewritten (`TimelineState.timelineId` is a string, GameMaker's real `timeline_index` is a numeric asset index with `-1` as its sentinel, and there's no lossless way to answer `timeline_index != -1` from a string id without inventing a fake numeric encoding). Proven end to end by `gms2-timeline-codegen.test.ts` (a real object's Create event produces this exact text) and `GmsRuntime.test.ts` (the exact emitted call shape, executed for real via `GmsProjectRuntime`, attaches/re-targets/removes a live `TimelineState`).

`sequence_index = sqFoo;` was researched for this same pass and turned out not to exist — GameMaker has no per-instance `sequence_index` instance variable; real Sequences are asset/layer-scoped (`layer_sequence_create(layer, x, y, sequence)`, confirmed against manual.gamemaker.io's Sequences reference pages), never a per-instance assignment the way `timeline_index` works. There is therefore no GML source shape analogous to `timeline_index` to rewrite for `GmlSequenceState` — `entity.add(GmlSequenceState, {...})` remains real and exercised directly by tests, but wiring a real GML source pattern to it is not a transpiler rewrite this pass could honestly invent; it would need a real design decision about which entity a room-layer sequence instance corresponds to, which is a genuine, separate, not-yet-started follow-up.

### GMS2 rendering built-ins: `sprite_index` / `image_*` / `depth` transpile onto real `Sprite`/`Transform` fields

Found by reading a real generated `.behavior.ts` file end to end, not assumed: `sprite_index = spr_foo;` — GameMaker's extremely common per-instance sprite-swap idiom (idle/walk/attack/hurt state machines) — was falling through to `gms2-transpile.ts`'s generic "auto-declare on first bare assignment" pass. That pass only protects the _assignment target_ from throwing; it does nothing for a bare identifier used as a _value_, so `spr_foo` on the right-hand side stayed a genuinely undeclared identifier and threw `ReferenceError` the moment the generated function actually ran. Since a sprite-swap state machine touches at least `sprite_index` in nearly every real GameMaker object, this was a near-universal runtime crash on first play, not an edge case.

`gms2-transpile.ts` now rewrites seven real per-instance rendering built-ins for real, all targeting fields this engine's `Sprite`/`Transform` components already have (`components/Sprite.ts`/`components/Transform.ts`) — confirmed against `RenderPipeline._syncOne()`, which is what actually reads each of these onto the rendered PixiJS sprite every frame:

- **`sprite_index`** → `Sprite.texturePath`. A bare identifier (the common real shape, `sprite_index = spr_dad_hug;`) is quoted into this importer's own real texture-path convention, `./assets/sprites/<name>/frame_0.png` — the exact one `gms2-codegen.ts`'s `buildObjectPrefabJSON`/`buildSpriteAsset` already use for an object's own initial `spriteId`, so a `sprite_index` assignment and that initial sprite can never disagree on what a sprite's texture path is. GameMaker's own documented sentinel, `sprite_index = -1` ("remove the sprite from an instance"), resolves to `""` — `Sprite.texturePath`'s own default, already meaning "no texture" everywhere else in this engine. An equality comparison against a bare sprite-asset identifier on either side (`if (sprite_index == spr_dad_idle)`, the other extremely common real shape) is resolved the same way, before the generic bare-read rewrite runs — otherwise the identifier on the comparison's other side would be left unresolved and crash exactly the way the write side used to. A bare read of `sprite_index` itself becomes a safe `_entity.get(GmlActions.Sprite)?.texturePath ?? ""`. Anything that isn't a bare identifier or `-1` (a variable, another instance's `sprite_index`, a ternary) is assumed to already evaluate to a real texture-path string and passed through unchanged — this importer has no way to resolve an arbitrary runtime expression to an asset name ahead of time and doesn't pretend to.
- **`image_angle`** → `Transform.rotation` (not `Sprite`, which has no rotation field of its own — `RenderPipeline` reads `pixiSprite.rotation` from `Transform.rotation`). GameMaker's own value is degrees; this engine's is radians (matching pixi's convention), converted both ways with the exact `* Math.PI / 180` / `* 180 / Math.PI` factor `gmlCamera.ts`/`gmlProjection.ts` already use for every other GML-degrees-to-engine-radians field.
- **`image_xscale`/`image_yscale`** → `Transform.scaleX`/`.scaleY` (same reasoning as `image_angle` — `Sprite` has no scale fields). No unit conversion; both default to `1` on both sides.
- **`image_alpha`** → `Sprite.alpha`. No conversion; both default to `1`.
- **`image_blend`** → `Sprite.tint`, reusing the exact `0xBBGGRR`→`0xRRGGBB` conversion `compat/gmlActions.ts`'s `action_sprite_color` already implements for the DnD "Set Sprite Colour/Blending" action, not a second copy of it. Unlike `timeline_index`'s deliberately-unrewritten read side, a bare read of `image_blend` is a real, exact round trip back to GameMaker's BGR ordering (`Sprite.tint` is a plain RGB integer, so converting it back is lossless — there's no encoding ambiguity here the way there is between `TimelineState.timelineId`'s string and GameMaker's numeric `timeline_index`).
- **`depth`** → `Sprite.depth`, but with a deliberate sign flip, not a direct copy. manual.gamemaker.io's Depth reference page is explicit that a _lower_ `depth` value draws that instance _in front of_ one with a higher `depth` (its own canonical example: depth `-100` draws in front of depth `0`). This engine's `Sprite.depth` sorts the opposite way — `RenderPipeline` (`_syncOne()`/`_syncProjected()`) writes `pixiSprite.zIndex = sprite.depth` straight through, and PixiJS's own `zIndex` convention is "higher draws on top" — confirmed consistent with `systems/LayerSystem.ts`'s own doc comment ("lower depth within the same layer ... also behind"). So a _higher_ `Sprite.depth` draws in front here, the exact inverse of GameMaker's _lower_-draws-in-front rule. Both the write (`depth = -100;` → `_sp.depth = -(-100)`, i.e. `100`) and the bare read (`_entity.get(GmlActions.Sprite)?.depth ?? 0`, negated) apply the identical `-` flip, so GML code that writes then later reads its own `depth` sees its original, un-flipped value back — a real, exact round trip, not an approximation, the same "flip once each direction, prove it round-trips" shape `image_blend`'s BGR↔RGB conversion above already uses.

**`image_index`/`image_speed` are real, multi-frame animation is real, and this superseded the old honest gap.** This used to be documented here as a deliberate non-goal — the sprite importer only ever copied a sprite's first frame, and `Sprite` had no per-frame state to receive these into. Both are now real:

`Sprite` (`packages/engine/src/components/Sprite.ts`) gained four fields, kept directly on the component rather than a sibling one — a multi-frame sprite is still "one visual thing this entity shows", not a second concern (see "Component types are identity keys" above for why a component's shape can change like this without breaking existing single-frame entities: `frameCount` defaults to `1`, so an entity that predates this change reads back byte-identical behaviour). `frameCount` (default `1`) is the sprite's real frame count; `currentFrame` (default `0`, a float — GameMaker's own `image_index` is a float too, so a fractional `frameSpeed` accumulates correctly rather than truncating every tick) is the frame currently displayed; `frameSpeed` (default `1`, matching a fresh GameMaker instance's default `image_speed`) is frames advanced per engine tick, exactly GameMaker's own real per-_step_ (not per-_second_) unit (confirmed against manual.gamemaker.io's Image reference pages: `image_speed` can be fractional, `image_index` wraps via modulo against the frame count when looping); `loop` (default `true`, GameMaker's own default for `image_speed > 0`) selects wrap-via-modulo vs. clamp-at-last-frame — GML itself has no per-instance way to express "stop at the last frame", but a one-shot death/hit animation is a real, common authoring need, so it's exposed as a plain field rather than left unmodelled.

`texturePath` doubles as a **template** for a multi-frame sprite: `frameCount > 1` means it contains the literal substring `"{n}"` (the GMS2 importer's own convention, `./assets/sprites/<name>/frame_{n}.png`, matching the `frame_0.png`/`frame_1.png`/… files `buildSpriteAsset` already writes to disk — every frame, not just the first, per `convertGms2Sprite`'s own `frames[]` array). `resolveSpriteFramePath` (exported from `components/Sprite.ts`) is the one shared function that turns `texturePath`+`currentFrame`+`frameCount` into the actual path to load this tick — a no-op for an ordinary `frameCount <= 1` sprite, so it's byte-for-byte the pre-animation behaviour in that case. `RenderPipeline._syncOne()`/`_syncProjected()` call it before touching the texture cache, so the cache is keyed by the _resolved_ per-frame path — each frame is a genuinely separate cached/loaded `Texture`, not a runtime spritesheet slice (no slicing is needed at all, since the importer already emits one PNG per frame).

`SpriteAnimationSystem` (`systems/SpriteAnimationSystem.ts`) is the new engine system that actually advances `currentFrame` — general-purpose, not GML-specific, the same "any game using a multi-frame `Sprite` benefits" scope `LightingSystem`/`TimelineSystem` already have. `Game.ts`'s shared `runFrame()` helper calls it once per loaded scene (main + every overlay) every tick, after physics settles and before coroutines/`onUpdate` — the same "engine-driven state settles before user code runs" ordering physics/actors already follow. It's `dt`-independent by design (advances by a whole `frameSpeed` per `update()` call, not `frameSpeed * dt`), matching GameMaker's own per-step unit. A `frameSpeed` of `0` never advances (GameMaker's own "static" convention), and a `frameCount <= 1` sprite is skipped entirely — no per-frame cost for the overwhelming majority of non-animated sprites in a typical game.

The GMS2 importer side: `SpriteAsset` (`gms2-sprite-import.ts`) gained an optional `frameSpeed`, read from the sprite's real `.yy` `sequence.playbackSpeed`/`playbackSpeedType` (confirmed against a real project sprite: `playbackSpeed: 15.0, playbackSpeedType: 0`) — `playbackSpeedType: 1` (frames per game-step) needs no conversion at all, since it's already `Sprite.frameSpeed`'s own unit; `playbackSpeedType: 0` (frames per second, GameMaker's own default) is converted by dividing by an honestly-documented assumed 60 steps/second (`ASSUMED_STEPS_PER_SECOND`) — this importer has no per-project room "Speed" setting to read for a real conversion factor, so a project that actually runs at a different step rate gets an approximation, not silently-wrong precision. `buildSpriteAsset` (`gms2-codegen.ts`) already copied every frame's PNG before this pass (this file previously, inaccurately, documented it as copying only `frame_0.png` — confirmed by reading the function: it always looped `sprite.frames`) — what actually changed is the emitted descriptor and texture-path convention: a multi-frame sprite gets the `"{n}"`-templated `texturePath` plus `frameCount`/`frameSpeed` fields; a single-frame sprite keeps the old literal `frame_0.png` path unchanged. `buildObjectPrefabJSON` now reads the object's initial sprite's own real frame count/speed (via `convertGms2Sprite`, wrapped in try/catch so a sprite that itself failed to import doesn't also fail the object's prefab) and seeds `frameCount`/`frameSpeed` overrides on the initial `Sprite` component whenever it's genuinely multi-frame — a GMS2 object with an animated sprite plays its animation from frame 0 the instant it spawns, matching GameMaker.

`gms2-transpile.ts` rewrites `image_index`/`image_speed` onto `Sprite.currentFrame`/`frameSpeed` — plain numeric passthroughs (no unit conversion, no equality-comparison special-casing, no round-trip formula, unlike `sprite_index`'s asset-name quoting or `depth`'s sign flip), following the exact established pattern (bare-identifier/compound-assignment rewrite, the `(?<!\.\s*)` dotted-reference exclusion guard, the `(?<!\/\/[^\n]*)` comment guard). A direct `image_index = 0;` assignment simply overrides that tick's displayed frame — `SpriteAnimationSystem` re-advances from wherever it's left on the next tick regardless, matching real GameMaker (writing `image_index` mid-step doesn't disable subsequent `image_speed` advancement).

Verified end to end against the real, full a real project: 63 of its sprites converted as genuinely multi-frame (2+ real frame PNGs each, not synthetic), 7 object prefabs seeded with real `frameCount`/`frameSpeed` overrides, and a full-project `tsc --noEmit` sweep of the regenerated output dropped from 862 error lines (this file's last documented sweep) to 798 — the two remaining `image_index`/`image_speed`-related lines are both a real, already-documented dotted-reference case (`inst.image_speed`, unresolvable by this transpiler, correctly left untouched), not a regression. Tests: `packages/engine/src/__tests__/SpriteAnimationSystem.test.ts` (frame advancement math, loop wrap including a negative `frameSpeed`, clamp-when-not-looping, fractional accumulation, `frameSpeed: 0` never advancing, `resolveSpriteFramePath`'s template resolution); `packages/engine/src/__tests__/RenderPipeline.test.ts` (a multi-frame sprite's rendered texture actually changes, and reloads through the real texture cache, as `currentFrame` advances); `packages/toolchain/src/__tests__/gms2-sprite-animation.test.ts` (real multi-frame `.yy` parsing including `playbackSpeed`/`playbackSpeedType`, `buildSpriteAsset` copying every frame file, `buildObjectPrefabJSON` seeding `frameCount`/`frameSpeed`, a full `importGMS2Project` end-to-end pass); `packages/toolchain/src/__tests__/gms2-transpile.test.ts`'s `"image_index / image_speed — multi-frame sprite animation"` block (write/read/compound rewrites, the dotted-reference guard, the comment-apostrophe-masking guard, a real `new Function()` runnability check).

Proven end to end against a real, full GameMaker project (not just synthetic fixtures): re-running the importer and reading the real generated `obj_dad.behavior.ts`, `obj_enemy_mreg.behavior.ts`, `obj_swing_axe.behavior.ts`, and `obj_hedgehog.behavior.ts` confirmed every one of these rewrites firing correctly on real GML source, including the exact `sprite_index = spr_dad_hug;`/`sprite_index = spr_dad_idle;` state-machine shape that surfaced the original bug. Synthetic regression coverage lives in `gms2-transpile.test.ts`'s `"transpileGML — GMS2 rendering built-ins (sprite_index/image_*)"` block.

**Two real interaction bugs this pass introduced, found and fixed by a second full-project pass — both hard `SyntaxError`s, not degraded output.** (1) The pre-existing "`if (a) <trailing condition continuation>`" pass (the one that turns `if (a) >= b { ... }` into `if ((a) >= b) { ... }`) has no `{` on the same line to anchor against for a bare, brace-less `if (cond) stmt;` — its lazy match kept expanding _past_ the body statement's own `;`, across unrelated following statements, until it found some later, wholly unrelated `{`, fusing the condition, the (now IIFE-rewritten) body, and an unrelated following statement into one broken `if (...)`. Confirmed against a real object's `Step_1.gml`: `if (sign(hsp) != 0) image_xscale = sign(hsp) * other.size;` followed by an unrelated `image_yscale = other.size;` and a later braced `if`. Fixed by bailing out of that pass whenever the captured span contains a `;` — a genuine trailing-condition continuation is always an expression and never contains one, so this only ever excludes cases that were actually a full statement. (2) None of `sprite_index`/`image_angle`/`image_xscale`/`image_yscale`/`image_alpha`/`image_blend`/`timeline_index`/`timeline_running`/etc.'s rewrites were guarded against a _dotted_ reference to another instance's field (`inst.image_xscale = imgx;`, a real, confirmed shape in a real project's own script) — GML allows writing/reading another instance's field through a dot reference, which this transpiler has no way to resolve, but the rewrite fired anyway and produced `inst.(() => { ... })();`, a dangling `.` with no property name. Fixed with the same `(?<!\.\s*)` guard `alarm[n] = expr`'s own dotted-reference exclusion already established — a dotted reference is now left untouched (an honest unresolved identifier) rather than misrewritten against the current entity. Both confirmed via a real `tsc --noEmit` run against the real project's full regenerated output (every `.behavior.ts` file, not a handful) before and after the fix — the same rigor gap ("looked right on a few files" vs. "verified against literally everything") that let the original bug through despite passing review on a smaller sample.

### GMS2.3+ syntax and array functions: struct/function literals already pass through, `static` is wired to a real closure-scoped store, array functions are wired

GMS2.3 introduced struct literals (`{a: 1, b: 2}`), function/method literals (`function() {...}`, including one referencing `self`/`other`), and `static` declarations inside a function. Checked by hand against `transpileGML` with synthetic sources (`gms2-transpile.test.ts`'s "GMS2.3+ struct/static/function literal syntax" block): a struct literal and a function literal (including one whose body reads `self`/`other`) both pass through this transpiler completely unchanged and are already valid JS as-is — no rewrite pass ever touches them, and none needed to.

**`static x = 0;` inside a function body is now real, not the honest gap it used to be.** GML's `static` declares a variable that persists across calls to that specific function/method — shared across every call to a script function, across every instance calling the same struct-constructor method, and (confirmed against GameMaker's manual/community docs on object-event statics) across every instance of an object using the same compiled event handler too, since GameMaker treats all three as "one function, one static slot" regardless of how many times it's invoked or by whom. `static` is only valid JS syntax inside a `class` body, so it can't be emitted verbatim. `gms2-transpile.ts`'s new rewrite pass (the "GML `static` variables" section, right after codegen assigns each generated function a stable `functionId`) rewrites each top-level `static <name> (= <expr>)?;` declaration into a lazy-initialised read/write against `packages/engine/src/compat/gmlActions.ts`'s new `gmlStatics: Record<string, unknown>` — one process-global, string-keyed store, not a `WeakMap`/`Map` keyed by `World`, because GML's `static` is explicitly _not_ per-instance or per-world: it's one slot per generated function for the whole process lifetime, which is exactly this object's own lifetime. Every bare reference to that name within the same declaration's function body is rewritten to read/write the same slot. The slot key is `<functionId>::<name>::<declarationOccurrence>`, so two different generated functions declaring a same-named static can never collide, and two same-named statics inside the same function (impossible in valid GML, but defensive regardless) don't either. `gmlStatics` is re-exported from `packages/engine/src/index.ts`. Proven by `gms2-transpile.test.ts`'s new tests: a static persists its value across two separate calls to the same generated function, its initializer runs exactly once, and two differently-named generated functions with a same-named static don't collide.

**Array functions are real and wired**, the actual high-value ask GMS2.3 array manipulation represents: GameMaker's arrays are always plain, dense, dynamically-growable lists — exactly what a native JS `Array` already is — so `compat/gml.ts` gained `array_length`, `array_create`, `array_resize`, `array_push`, `array_pop`, `array_insert`, `array_delete`, `array_sort`, `array_contains`, `array_map`, `array_filter`, `array_reduce`, each a thin, honest wrapper over the matching native `Array` method (`array_push` → `.push(...)`, `array_sort` → `.sort(...)` with GameMaker's own boolean-or-comparator-function `order` argument, etc.), threaded through `gms2-transpile.ts`'s existing `THREADED_PURE_FUNCTIONS` list — the same "no `_entity`/`_ctx` needed, no object-name quoting" pass `sign`/`lengthdir_x`/`array_length_1d` already used. `array_map`/`array_filter`'s callback argument order (`(value, index)`) and `array_reduce`'s (`(accumulator, value)`) are confirmed against GameMaker's own manual to match `Array.prototype.map`/`.filter`/`.reduce`'s own callback order exactly, so no argument reordering was needed in the wrapper. `array_length_1d` (the pre-2.3 alias, already wired) is kept alongside the real `array_length` name rather than replaced. Per the user's own "you decide if warranted" instruction and this file's existing "triage real, common, high-value gaps, not a total compiler" precedent, the rest of GML's built-in surface (ds*\* beyond what's already wired, `physics*\*`, obscure string/date functions, …) was deliberately not chased in this same pass.

### Multi-camera rendering: `RenderSystem.renderMultiCamera()`, N `RenderTexture` passes plus a composite pass

GameMaker's real camera/view model allows up to 8 simultaneously active camera/view slots, each with its own world position/zoom/rotation and its own screen viewport rectangle. `compat/gmlCamera.ts`'s `buildActiveGmlCameraViewports(ctx)` already collected this per-frame (every enabled, visible view slot's `GmlCameraViewport` — position, zoom, rotation, `viewWidth`/`viewHeight`, and the `screenX`/`screenY`/`screenWidth`/`screenHeight` rectangle it draws into) before there was anywhere real to send it. `RenderSystem.renderMultiCamera(viewports)` is that destination, and it is real, tested, and live — not aspirational.

`RenderSystem.ts` declares its own `CameraViewport` structural interface rather than importing `GmlCameraViewport` from `compat/gmlCamera.ts` — the same layering rule `RenderPipeline`'s `TileLayerSource` interface already follows for `@emptysock/tilemap`: core engine rendering must stay usable by any game, not just a GML-imported one, and `compat/` (a GameMaker-specific translation layer) depends on the engine, never the other way around. `GmlCameraViewport` is structurally identical and satisfies `CameraViewport` with no adapter.

The technique: for each active viewport, `renderMultiCamera()` writes that viewport's own position/zoom/rotation onto `_stage` using the exact convention `CameraSystem.update()` already writes (`stage.x = -viewport.x`, `.y = -viewport.y`, `.scale = viewport.zoom`, `.rotation = viewport.rotation` — so a single-camera game and a multi-camera one agree on what "camera position" means), then renders `_stage` into that viewport's own offscreen `RenderTexture` (sized to `viewWidth`/`viewHeight`) via pixi v8's real object-form `renderer.render({ container, target })` API — the same API `syncLighting()`'s lightmap pass above already uses, and the one CLAUDE.md's `SceneTransitionManager` entry names as real and available. Once every viewport has rendered, each `RenderTexture` is drawn as a plain `Sprite` quad positioned/sized at that viewport's own screen rectangle onto a compositor `Container`, and that compositor renders straight to the real canvas in one final pass.

This is genuinely opt-in and does not touch the ordinary single-camera path: `renderMultiCamera()` saves `_stage`'s transform before its per-viewport passes and restores it exactly before returning, so a `CameraSystem` driving `render()` never sees any effect from a call here, and `render()` itself is entirely unmodified — call `renderMultiCamera()` instead of `render()` for a frame that wants GameMaker's multi-view compositing, call `render()` as before otherwise. One `RenderTexture`/`Sprite` pair is cached per viewport `id` and reused across calls (resized only when that viewport's `viewWidth`/`viewHeight` actually changed, the same "don't reallocate a GPU resource every frame" discipline `_lightMapTexture`/`_postProcessFilters` already follow); a viewport id that stops appearing in the list has its cached texture/sprite destroyed and dropped on the next call.

This is a real N-full-render-pass-per-frame cost, the same caveat `SceneTransitionManager`'s and `syncLighting()`'s own doc comments already raise — bounded by how many camera slots a game actually activates at once, not GameMaker's fixed 8-slot ceiling, but this method does no profiling of its own; a game leaning on several simultaneous cameras still needs real device profiling before shipping that configuration. `RenderSystemMultiCamera.test.ts` covers: two viewports with different position/zoom producing two genuinely distinguishable offscreen passes (asserted on the real transform values `_stage` carried into each `renderer.render()` call, and on each pass targeting a distinct `RenderTexture`); rotation applied per-pass; each viewport's texture drawn as a sprite at its own correct screen rectangle in the final composite pass; the pre-call `_stage` transform restored exactly afterward (proving no leakage into the single-camera path); texture/sprite reuse across calls when a viewport's size is unchanged; and cache eviction when a viewport id drops out of the list.

### Pseudo-3D projection: `compat/gmlProjection.ts` writes four corners, `RenderPipeline` renders them via a real `PerspectiveMesh`

GameMaker's legacy pre-2.3 pseudo-3D family (`d3d_set_projection_ortho`/`d3d_set_projection_perspective`, `d3d_transform_set_translation`/`_rotation_x`/`_rotation_y`/`_rotation_z`/`_scaling`/`_identity`) is real, old GameMaker content's actual mechanism for faking depth in an otherwise-2D game — see RELEASE_PASS.md's 2026-09-24 research pass for why this legacy per-instance-transform family was targeted over the modern `camera_set_proj_mat` 4x4-matrix API (real old content overwhelmingly uses the former). This engine renders it with pixi.js core's real, already-installed `PerspectiveMesh`/`PerspectivePlaneGeometry` (zero new dependency) — a 2D mesh with a UV-level perspective correction across four independently-movable corner points, clockwise from top-left. Per `PerspectiveMesh`'s own doc comment: "this is not a full 3D mesh, it is a 2D mesh with a perspective projection applied to it" — no Z-buffer, no real camera matrix, no true 3D, which matches what GameMaker's own legacy pseudo-3D tricks were already faking.

**The compat layer, `compat/gmlProjection.ts`**, is a sibling to `gmlActions.ts`/`gmlCamera.ts`, same `(entity, ctx, ...)`-adjacent shape (here `(entity, ...gmlArgs)`, no `ctx` needed — every function only touches its own entity's corner state). It computes four `(x, y)` corners per call and writes them onto the entity's `Projection3D` component (`components/Projection3D.ts` — `Serializable`-only, like every component; `active: false` by default means "render as a normal `Sprite`, ignore these corners entirely"). A per-entity `(World, eid)`-keyed side-table (`quadByWorld`) holds the _base_ untransformed quad size (`width`/`height`) a `d3d_transform_set_*` call transforms — the same "component holds the derived result, a side-table holds the mutable working state" split `VisualScriptState`'s evaluation scope and `PhysicsBody`'s callbacks already use; `clearGmlProjectionState(entity)` clears it, for the same pooled-id-reuse reasoning every other per-`(World, eid)` side-table in this codebase needs.

GameMaker's real `d3d_transform_set_*` functions **replace** the current world matrix rather than composing with it — this compat layer mirrors that exactly: calling `d3d_transform_set_rotation_z` then `d3d_transform_set_translation` produces the plain translated quad, not a rotated-then-translated composite, because each function independently recomputes all four corners from the entity's base quad size and its own arguments alone. `d3d_transform_set_rotation_x`/`_y` (real GameMaker: rotation about the horizontal/vertical axis, tilting the plane toward/away from the viewer) has no literal analogue on a flat four-corner 2D mesh — approximated as a `cos(angle)` shrink of the one edge that "recedes" (top edge for `_x`, left edge for `_y`), centred: `cos(0°) = 1` (untilted, exact rectangle), `cos(90°) = 0` (that edge collapses to a point). This is a real, deterministic, hand-verifiable trig formula for the one thing a flat mesh _can_ represent about that kind of tilt (foreshortening of the far edge) — not a claim of matching GameMaker's real 3D matrix output. `d3d_set_projection_perspective` (GameMaker's real function takes an eye/look-at/up vector triple — a genuine 3D camera a four-corner mesh has no input space for) is approximated as a trapezoid: the far (top) edge narrowed to a fixed, documented `PERSPECTIVE_FAR_SCALE` (0.5) of the near (bottom) edge's width, centred — the standard "railroad tracks converging toward a horizon" shape a flat ground plane's real perspective projection produces. `d3d_set_projection_ortho` has no perspective term at all, so it is an exact, hand-verifiable rotated rectangle with no approximation involved. Every one of these formulas is covered by `gmlProjection.test.ts`'s hand-derived expected corner values (computed independently of the implementation, using angles — 0°/90°/45°/30°/180° — chosen so the trig terms are exact or floating-point-negligible), not just "did not throw" — including a dedicated test proving the "replace, not accumulate" semantic.

**The render-side wiring, in `RenderPipeline._syncOne()`**: an entity with `Transform`+`Sprite` and no `Projection3D` (or one whose `active` is `false`, the default) renders exactly as before this feature existed — a plain `PixiSprite` positioned from `Transform`. An entity with an _active_ `Projection3D` instead renders through `_syncProjected()` — a real `PerspectiveMesh` per entity (cached per eid in `SceneTracking.meshes`, the same "one map, disjoint from `sprites`, an eid is only ever tracked in one of the two at a time" shape), whose corners are copied straight from `Projection3D.x0..y3` via `PerspectiveMesh.setCorners()` — no reinterpretation, since both sides already agree on "clockwise from top-left" (`Projection3D`'s own doc comment states this explicitly). A projected entity's `Transform` is deliberately **not** applied to the mesh's position — `gmlProjection.ts`'s corners are already-absolute positions (a `d3d_transform_set_translation` call bakes the translation directly into the corner coordinates, the same way a real GameMaker instance's `x`/`y` would already be baked into its world matrix), so applying `Transform` on top would double-position the mesh. Texture loading is shared with the plain-sprite path (`_applyTexture()` was generalised to take any `{ texture: Texture }` target, since both `PixiSprite` and `PerspectiveMesh` expose a settable `.texture`) — same cache, same fallback-to-`Texture.WHITE`-on-empty-path behaviour. An entity that flips `Projection3D.active` (or gets destroyed) has its stale renderable — mesh or sprite, whichever no longer applies — torn down on the very next sync, via the same `_removeSprite`/`_removeMesh` pruning `_pruneUnseen()` already runs for every entity every frame.

### GMS2 playability blockers found by the smoke test, fixed for real: per-sprite collision extents, and object inheritance/variable-definitions

The playability smoke test's own honest findings above (`obj_player.x` never moving, `obj_enemy`'s `grv`/`hp`/`has_weapon` reference errors) were two real, previously-undiscovered gaps, both fixed this pass, plus one still-open finding this pass's own investigation surfaced.

**Real per-sprite collision extents.** `Sprite` (`packages/engine/src/components/Sprite.ts`) gained `width`/`height` fields (`0` default = genuinely unknown). `gms2-codegen.ts`'s `buildObjectPrefabJSON` now reads an object's initial sprite's real `.yy` `width`/`height` (already parsed by `convertGms2Sprite`, which already exposed them on `SpriteAsset` — no new parsing needed) and seeds them as `Sprite` overrides. `compat/gmlActions.ts`'s `spriteHalfExtents()` now reads `Sprite.width`/`.height` when both are `> 0`, falling back to the old fixed 16px half-extent (32px square) only when genuinely absent. Researched GameMaker's own collision-mask semantics: sprites can use a non-bbox precise mask, but every real sprite in a real project uses a plain rectangular mask, so a real-dimensions bounding box is the correctly-scoped fix — a full per-pixel mask system would be over-engineering here. Confirmed via the smoke test: `obj_player`'s real box is 10×29 (was a fixed 32×32), `obj_wall`'s is 32×32 — no longer permanently mismatched.

**Real GameMaker object inheritance and GMS2.3+ Variable Definitions — two genuinely different mechanisms, both real gaps, both now implemented.** Investigating `obj_enemy`'s `grv`/`hp`/`has_weapon` found they are **not** set via inheritance at all (a fresh hypothesis this pass initially assumed and then disproved by reading the real `.yy`) — they're GMS2.3+ "Variable Definitions", a real per-object `.yy` `properties` array of typed instance-variable defaults declared on the object resource itself, never in any `.gml` file. `resolveGmlObjectProperties()` (`gms2-codegen.ts`) walks the real `parentObjectId` chain (root-most first, so a child's own properties override a parent's same-named one — this **is** real inheritance, confirmed via GameMaker's manual's Object Inheritance page: "if the child object does not have an event that the parent has, then it will use the parent's event") and reads `varType: 3` as boolean (`"True"`/`"1"` → `true`), everything else as a number when it parses as one, else a raw string (a value that's itself another property's name as an unevaluated expression — real, observed: `obj_enemy.yy`'s own `hsp` property has the literal value `"walksp"` — is read at face value, not evaluated, an honest narrow gap). The resolved names are seeded into `objectImplicitVars` (so a bare _read_ of `grv`, never _assigned_ in any `.gml` file, is recognised the same as an ordinary implicit instance variable) and emitted as `GmlActions.setGmlVar(...)` calls prepended to the generated `onCreate`, before the transpiled Create body runs — matching GameMaker's real timing.

Separately, real object-inheritance **event fallback** is also now implemented: `buildObjectBehavior`'s `buildMethod` searches the real `parentObjectId` chain (`resolveGmlObjectChain()`) for each event slot in child-to-root order, using the nearest ancestor that actually has that event file when the object itself has none — a generated comment names which ancestor a fallen-back event came from. `event_inherited()` (real, confirmed usage: one real call site, `obj_crate/Draw_0.gml`) is not wired — left as an honest unresolved identifier, the same as other genuinely-unmodelled GML — since it needs the compiled parent function reused _inside_ a child's own override, a harder problem than the no-override case this pass solved; a real, separate, named follow-up.

Confirmed via the smoke test: `obj_enemy`'s `grv`/`hp`/`has_weapon` `ReferenceError`s are gone (all three: `hp` turned out to be a real `obj_pShootable` parent property too, resolved by the same chain walk).

**A separate, real, still-open finding from this pass's own investigation, not fixed here:** with real collision extents in place, `obj_player.x` still does not move under held `vk_right` — re-traced (not still attributed to the old 32×32 box) to `obj_player`'s own Step code reading `key_right` via `obj_input.key_right`, a real cross-instance dotted reference (see the cross-instance-references entry above) that depends on `obj_input`'s own input-polling script (`scr_get_input`) running every Step against a live `obj_input` instance — a real, separate, not-yet-traced gap, left honest rather than guessed at further within this pass's scope. `gms2-playability-smoke.test.ts`'s own comments were updated to reflect this corrected root cause. A minor, separate, unrelated finding from the same run: a bare `noone` value reference (`obj_enemy`'s own `else my_gun = noone;`) is a real, still-unwired GameMaker constant — left open, the same class of gap as the already-documented bare `obj_player`-as-value case.

### GMS2 playability: the `vk_right` movement gap was `Scene.spawn()` never stamping `Meta.name`, not a transpiler bug

The prior pass's own "still-open finding" above (`obj_player.x` never moving under held `vk_right`) was traced to completion, not re-guessed. `scr_get_input`'s codegen and `obj_player`'s `key_right = obj_input.key_right;` -> `getGmlObjectVar(_entity, _ctx, "obj_input", "key_right")` rewrite were both re-verified correct — the real cause was one level deeper: `getGmlObjectVar` resolves its target instance by scanning every live entity's `Meta.name` (see the cross-instance-references entry above), but `Meta.name` was only ever stamped from a prefab's own name by `loadSceneFile()`'s `stampPrefabNameOntoMeta()` — a direct `Scene.spawn(prefab)` call, with no `loadSceneFile()` involved, produced an entity with no resolvable object-type identity at all. This is not a test-only gap: `compat/gmlActions.ts`'s `action_create_object` (the function `instance_create`/`instance_create_layer` both route through) called `ctx.scene.spawn(prefab, { x, y })` directly, the exact same bypass — so **any** real GameMaker project's runtime-spawned singleton object (an input manager spawned once from a controller's Create event, a bullet, a pickup, anything created via `instance_create`/`instance_create_layer` rather than room-placed) got an entity `place_meeting`/`onCollideWith<Type>`/`getGmlObjectVar` could never find by object-type name, silently, forever.

Fixed by exporting `stampPrefabNameOntoMeta` from `SceneFile.ts`/`index.ts` (it was a private, unexported function) and calling it from `action_create_object` right after the real spawn, reusing the one existing implementation rather than duplicating the "if no `Meta`, add one; if `Meta.name` is empty, fill it in; never overwrite an explicit name" logic a second time. `gms2-playability-smoke.test.ts`'s own manual `obj_input` spawn (which bypasses `action_create_object`, since it isn't reached via transpiled GML) now calls the same helper explicitly, matching what a real GML-driven spawn does automatically.

Confirmed via the smoke test with temporary debug logging (removed before finishing): a real run moved the player from `startX 160` to `endX 1752` over 400 frames of held `vk_right` — the test's assertion changed from "finite, unmoved" to `endX > startX + 50`. Vertical movement under gravity is unaffected (still asserted).

Full-project `tsc --noEmit` sweep before this pass: 344 error lines. After: 309. Full engine (640 tests) and toolchain (410 tests) suites pass. Tests: `packages/toolchain/src/__tests__/gms2-playability-smoke.test.ts` (updated — real movement assertion, corrected root-cause comment).
